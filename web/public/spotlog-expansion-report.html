현재 모바일웹·하이브리드 앱의 구현 범위를 기준으로 상용 서비스 전환, 국내 콘텐츠 확보 및 외국인 관광객 대상 확장 방안을 정리함.

요약 의견

Spotlog의 핵심을 랜드마크 영상 서비스가 아닌 실제 여행기를 읽고 자기 일정으로 복사하여 현장에서 사용하는 로컬 여행 가이드로 정의함. 현재 구현한 탐색·저장·일정 편집·여행기 상세 UI는 유지함. 상용화를 위해 회원·서버 저장·미디어 업로드·장소 검색·운영 안전 기능을 우선 구축해야 함. 국내 콘텐츠와 사용 흐름을 먼저 확보한 뒤 검증된 여행기에 영어 번역과 외국인 현장 정보를 추가하는 순서가 적절함.

PRODUCT여행기를 중심으로 구성함

장소는 일정의 재료로 활용함. 글·사진·동선이 결합된 경험을 최종 콘텐츠로 정의함.

SEQUENCE국내 운영 기반을 먼저 완성함

서울·부산·제주·경주·강릉에 집중하여 검증 가능한 콘텐츠와 사용 데이터를 확보함.

PLATFORM웹 본체와 앱 기능을 분리함

탐색·작성은 모바일웹을 유지함. 촬영·위치·오프라인·푸시는 앱이 담당함.

01 · CURRENT STATUS

현재 구성 및 판단

현재 화면은 제품 방향을 검증하는 기준선으로 활용함. 다만 데이터가 브라우저 내부에 있으므로 다중 사용자 서비스로 판단할 수 없음.

유지 대상

  • 추천 일정과 여행자 여행기가 롤링되는 메인 유지함
  • 지역·작성자·기간별 여행기 검색 흐름 유지함
  • 영상·지역 안내를 통한 장소 발견과 저장 유지함
  • 여러 여행, DAY 추가·삭제, 글·사진·장소 편집 유지함
  • 여행 상세, 지도 경로, 전체 여행 복사 흐름 유지함
  • 댓글·응원·작성자 등급·알림 설정 UI 재사용함

상용화 전 교체·추가 대상

  • localStorage를 회원 기반 서버 저장으로 교체할 필요 있음
  • 사진·영상 업로드, 변환, CDN 제공 기능 필요함
  • 조회·담김·댓글·등급을 서버 이벤트로 집계할 필요 있음
  • 카카오 장소 검색을 서버에서 연동할 필요 있음
  • 원격 푸시, 딥링크, 신고·차단·운영 도구 필요함
  • 실제 AI 호출과 비용·오류 통제 기능 필요함

기능별 현재 상태

구분현재 상태향후 조치
여행·장소 저장부분 구현 localStorage 사용 중서버 저장소와 계정 동기화로 교체 필요함
지도·경로기준선 MapLibre·OSM·OSRM 사용 중개발용으로 유지함. 운영 공급자와 SLA 별도 결정 필요함
AI 일정기준선 거리·체류시간 기반 로컬 생성안전한 대체 수단으로 유지함. 서버 AI 선택 추가함
소셜·푸시부분 구현 화면과 로컬 알림만 존재함실제 이벤트·기기 토큰·중복 방지 서버 필요함
하이브리드 앱부분 구현 WebView APK 확인 완료함오프라인·위치·촬영 기능 추가 후 스토어 앱으로 판단함
02 · SERVICE MODEL

서비스 확장 모델

사용자가 콘텐츠를 보는 단계에서 끝나지 않고 실제 여행과 다음 여행기 생산으로 이어지는 반복 구조를 구축함.

STEP 1발견영상·사진·검색·추천 여행기 제공함
STEP 2빠른 저장목적지 지정 없이 장소 저장함
STEP 3여행별 분류지역·기간별 보관함에 정리함
STEP 4일정 생성복사 또는 AI 초안 생성함
STEP 5실제 여행길찾기·완료·현장 기록 제공함
STEP 6여행기 발행글·사진·장소·동선 결합함
STEP 7복사·반응담김·댓글·등급을 작성자에게 환류함

영상·사진·안내 콘텐츠 운영 기준

표현 방식 통합

  • 풀영상, 사진 모션, 사진 이야기, 안내 목록을 병행함
  • 모든 형식에 동일한 Spotlog 장소 ID를 연결함
  • 모든 형식에서 동일한 저장 버튼과 저장 결과를 사용함
  • 원본 영상 보유 시 풀영상을 우선 활용함
  • 사진만 보유한 경우 모션·슬라이드 방식으로 제공함
  • 장소가 연결되지 않은 영상은 발견 피드에서 제외함

저장 방식 통합

  • 발견 단계에서는 빠른 저장함에 즉시 저장함
  • 저장 단계에서 여행 선택을 강제하지 않음
  • 지역을 자동 분류하여 저장 목록에 표시함
  • 동일 지역 3곳 이상 저장 시 여행 묶음을 제안함
  • 일정 생성 직전에 사용할 지역·보관함을 확정함
  • 저장 카드에 포함 여행과 DAY를 명확히 표시함
03 · IMPLEMENTATION ROADMAP

단계별 추진 순서

개별 화면을 단독 추가하지 않음. 다음 기능이 의존할 수 있는 데이터 기반부터 순차 구축함.

P0

회원·DB·권한·미디어 기반 구축

로그인, RLS, 서버 저장, 로컬 데이터 이전, 사진·영상 업로드 구성함. 공개 서비스 출시 차단 항목으로 지정함.

최우선
P1

장소 검색 및 여행별 보관함 구축

카카오 장소 검색을 서버에서 연결함. 한글명·주소·좌표를 고정 저장하고 빠른 저장함과 여행별 컬렉션을 도입함.

내부 알파
P2

편집·부분 복사·AI 기능 완성

자동 저장, DAY 이동·복제, 전체·DAY·장소 단위 복사, 검증 가능한 서버 AI 일정을 구현함.

국내 베타
P3

소셜·푸시·운영 안전 구축

조회·담김·댓글·팔로우, 목표 푸시, 신고·차단·운영자 처리 기능을 구축함.

국내 공개 전
P4

앱 전용 실제 여행 모드 구축

오프라인 일정, 현재 위치, 방문 완료, 사진·메모 대기열, 딥링크를 제공함. 단순 WebView 구조를 보완함.

앱 심사 전
P5

영어 로컬 가이드 베타 추진

검증된 국내 여행기에 영어 번역, 현장 정보, 지도 앱 선택, 한글 주소, 긴급 안내를 추가함.

04 · CONTENT ACQUISITION

국내 콘텐츠 확보 방안

전국 장소 수 확대보다 실제로 따라갈 수 있는 완성형 여행기 확보를 우선함.

서울

도심 산책·성수·궁·야간 코스 중심으로 구성함

부산

해안·시장·언덕 마을 이동 동선 중심으로 구성함

제주

동서 권역·날씨 대체 일정 중심으로 구성함

경주

역사·자전거·야간 유적 중심으로 구성함

강릉

바다·카페·당일·1박 코스 중심으로 구성함

초기 공개 목표 · 지역당 12~20개, 전체 60~100개의 완성형 여행기를 확보함. 당일치기·1박 2일·2박 3일 유형을 지역마다 확보함. 여행기별 원본 사진, 3곳 이상 장소, 이동 순서, 체류시간, 장점, 아쉬운 점을 포함함.

수급 방식

  • 운영자가 지역별 대표 여행기를 먼저 제작함
  • 지역당 2~5명의 초기 창작자를 모집함
  • 월별 주제와 작성 템플릿을 제공함
  • 호텔·게스트하우스에는 주변 하루 동선 작성을 요청함
  • 샘플·일반 글·광고·협찬을 명확히 구분함

작성자 동기 부여

  • 실제 전체·DAY·장소 담김 수를 제공함
  • 완독률과 실제 여행 완료 반응을 제공함
  • 댓글·응원·작성자 고정 댓글을 제공함
  • 초기 창작자·지역 가이드 배지를 제공함
  • 홈 추천과 지역 대표 노출 기회를 제공함
  • 가짜 조회수와 가짜 반응을 사용하지 않음
05 · GLOBAL EXPANSION

외국인 대상 확장 방안

국내 콘텐츠를 별도 서비스로 교체하지 않음. 동일 여행기에 번역 및 외국인 현장 정보 계층을 추가함.

구분적용 방안판단
콘텐츠한국어 원문과 영어 번역을 함께 관리함인기·신고율로 검증된 여행기부터 번역함. 원문 수정 시 재검토 상태로 변경함.
장소 정보번역명과 한글 원명·주소를 병기함현지인과 택시 기사에게 보여줄 큰 글씨와 복사 기능을 제공함.
지도앱 내 동선과 외부 지도 앱 선택을 병행함카카오맵을 국내 기본으로 안내함. Google·Apple·네이버 선택을 제공함.
현장 정보출구·예약·결제·짐·접근성 정보를 구조화함공식 사실과 작성자 방문 당시 경험을 구분하고 확인일을 표시함.
오프라인일정·좌표·한글 주소·작은 이미지를 저장함인터넷 장애 상황에서도 일정과 112·119·1330 정보를 확인하게 함.

언어 적용 순서

  • 1단계에서 한국어 UI와 국내 콘텐츠를 완성함
  • 2단계에서 한국어·영어 베타를 운영함
  • 3단계에서 일본어를 추가함
  • 4단계에서 중국어 간체·번체를 추가함
  • 추가 언어는 실제 방문자·검색·복사 데이터를 기준으로 결정함
06 · DATA & TECHNOLOGY

데이터·기술 구성 원칙

하나의 지도 또는 장소 공급자가 모든 정보를 제공한다고 가정하지 않음. 목적별 공급자를 분리함.

공급자·영역사용 범위운영 원칙
Kakao Local국내 업체명·카테고리·주소·좌표·전화·상세 URL서버 함수에서 호출함. 사진·다국어 콘텐츠 공급자로 사용하지 않음.
한국관광공사다국어 관광 설명 및 사용 허가 범위가 명확한 관광 이미지관광지 기준 정보에 활용함. 출처와 확인일을 저장함.
Google Places영어 장소 검색 보조 및 사진이 필요한 일부 장소비용과 필드 정책을 고려하여 선택적으로 호출함.
사용자 입력실제 경험·평가·사진·숙소 선택 이유·이동 팁공식 정보와 시각적으로 구분함. 방문 시점과 확인일을 표시함.
경로 공급자거리·이동시간·경로선실시간 교통 반영 여부를 명시함. 장애 시 예상치로 대체함.
생성형 AI일정 분배·번역 초안·글 구조화가격·영업시간·업체 사실을 생성하지 못하도록 검증함.

  • 여행 일정 및 여행기 편집을 제공함

  • 현재 위치와 실제 여행 모드를 담당함
  • 저장 여행 오프라인 열람을 담당함
  • 원격 푸시와 딥링크를 담당함
  • OS 공유 시트와 지도 앱 선택을 담당함
07 · FIRST 90 DAYS

90일 우선 실행안

화면 추가보다 실제 데이터가 생성·저장·조회되는 단일 완성 흐름 구축을 우선함.

1~4주

서버 기준선 구축

  1. 개발·스테이징 환경 분리함
  2. 회원·여행·장소·보관함 DB 구성함
  3. RLS 허용·거부 테스트 작성함
  4. 로컬 데이터 1회 이전 구현함
  5. 사진 업로드 최소 기능 구축함
5~8주

장소→보관함 흐름 구축

  1. 카카오 Local 서버 검색 연결함
  2. 직접 등록과 중복 처리를 구현함
  3. 빠른 저장함과 여행별 보관함 구현함
  4. 저장 장소→일정 생성 연결함
  5. 한국어·영어 장소 필드를 확정함
9~12주

내부 알파 검증

  1. 두 기기 동기화를 검증함
  2. 자동 저장과 작성 복구를 구현함
  3. 전체·DAY·장소 복사 이벤트를 기록함
  4. 5개 지역 콘텐츠 제작을 시작함
  5. E2E 테스트와 비용 계측을 적용함

최종 제안

현재 UI를 유지하면서 저장소와 공급자 연결을 상용 구조로 전환함.

다음 구현 단위

  • Supabase 개발 환경과 권한 구조를 구성함
  • 로그인 후 기존 로컬 데이터를 서버로 이전함
  • 카카오 장소를 서버에서 검색함

FINAL DIRECTION

국내에서 신뢰할 수 있는 여행기를 먼저 축적함.

서버 기반의 저장·복사·반응 데이터를 확보한 뒤 외국인 수요가 높은 여행기부터 영어로 확장함. 모바일웹은 콘텐츠 본체로 유지하고 앱은 오프라인·위치·촬영·푸시 기능을 담당하도록 발전시킴. 다음 개발은 로그인부터 장소 검색, 여행별 저장, 일정 생성까지 이어지는 세로 기능으로 추진함.

# Spotlog AI·지도 신규 구축: 실제 시작 순서

최신 모델 정책(2026-09-21): **소형 모델 기본 · 대형 LLM은 미해결 부분만 보완**. 일정 계산·검증은 우리 서버, 모델 호출은 Flowise 경유. 데이터 부족·지도 장애는 대형 호출 대상에서 제외. 간단 생성 우선·챗봇 향후 추가 유지. [상세 호출 기준](AI_MODEL_CASCADE_20260921.md)이 아래의 단일 생성형 모델 설명보다 우선.

2026-09-21 방향 갱신: **AI 간단 생성에서 글을 읽고 완성 일정 초안을 만드는 기능 우선. 챗봇 화면·대화 이력·이어 말하기는 향후 추가.** 기존 ‘저장 장소로 추천’ 유지. 맥미니의 Flowise는 초기 간단 생성에도 재사용할 자체 운영 실행 도구이며 AI 모델 자체나 필수 챗봇 화면이 아님. 신규 구축 범위는 Spotlog 서비스 백엔드·회원/장소/순위/여행 DB. [간단 생성 우선·챗봇 향후 연결안](FLOWISE_CHAT_ITINERARY_PLAN_20260920.md) 참고. 실제 Flowise 접속·서비스 서버·AI·지도 연결 구현 전.

2026-09-20 · 서버·DB·업체 순위 데이터 모두 없는 신규 구축 기준. 로컬 프론트 수정과 실행 계획이며, 유료 서비스 신청·키 발급·실제 API 연결·Git 반영은 하지 않았다.

## 먼저 결정할 구성

현재 React 웹과 Expo 앱 유지. 초기 구성안은 **우리 Spotlog 서버 + 우리 관리형 PostgreSQL(PostGIS·pgvector 지원) + 사진 저장소 + 자체 운영 Flowise + 외부 대화·일정 생성 AI + 외부 임베딩 AI + 네이버 지도**. 외부 대화·일정 생성 AI는 고객 문장의 조건 이해와 일정 제안 담당, 외부 임베딩 AI는 허가된 설명과 검색어를 검색용 숫자로 변환하는 역할. Flowise는 AI 호출·허용 검색 흐름 실행, 우리 서버는 권한·DB 사실·결과 검증·저장 담당. 특정 AI 제공자·모델은 미확정. 자체 모델 학습이나 GPU 서버 구매부터 시작할 필요 없음.

초기 고객 흐름: **간단 생성에 글 입력 → 조건 인식 → 장소·설명 검색 → 완성 일정 초안 → 상세에서 필요한 부분 수정 → 내 여행 저장**. 지역·기간 등 간단한 보조 선택과 저장 장소 추천 유지. 긴 설정·음식점/숙소 후보 고르기·챗봇 질의응답 왕복은 생성 전 필수 단계에서 제외. 날짜·시각과 자세한 배치는 생성 후 상세에서 보완.

향후 챗봇: **대화로 여행지 추천·찜 → 같은 일정 생성 기능 호출 → 같은 상세 수정·저장**. 대화 UI·맥락·세션만 추가하고 장소 검색·생성·검증·저장 기능은 공통 사용.

업체와 좌표를 연결하는 일은 모델 학습보다 먼저 해야 하는 DB 작업이다. ‘주안반점’의 특정 지점을 `placeId`로 등록하고 주소·좌표·분류·검수 상태를 붙인다. 업체 조직은 필요하면 `companyId`로 연결한다. 순위·사진·RAG 설명·여행의 방문은 같은 `placeId`를 참조한다. 같은 가게에 두 번 가면 방문을 나타내는 `visitId`는 별개다.

**순위와 좌표는 DB가 결정하고, AI는 검증된 후보 안에서 일정을 구성한다.** RAG는 사용권이 확보된 설명에서 취향·방문 이유를 찾는 부분이다. 업체 이름·좌표를 AI가 임의로 만들어 넣는 방식으로 구현하지 않는다.

## 직접 준비하실 일

| 순서 | 하실 일 | 준비 결과 | 이후 개발자가 할 일 |
|---|---|---|---|
| 1 | 고객 소유 계정인지 개발사 소유 계정인지 정하기 | 서비스 관리자·비용 책임자·개발자 초대 대상 | 개발/운영 권한과 환경 분리 |
| 2 | 첫 검증 지역 하나 정하기 | 예: 제주 서부 한 권역. 아직 확정된 지역은 없음 | 해당 권역의 장소 등록·지도·완성 일정부터 연결 |
| 3 | 장소 자료를 누가 확보·검수할지 정하기 | 담당자와 허가된 자료 목록 | 등록 화면·가져오기·중복 및 좌표 검수 기능 |
| 4 | 초기 추천 기준 정하기 | 운영자 추천/거리/취향 등 우선순위 | 버전이 있는 정렬 규칙과 추천 근거 저장 |
| 5 | API·서버 비용 한도와 도메인 담당 정하기 | 개발 예산, 운영 예산, 도메인/DNS 관리자 | 서버·DB·사진 저장·로그·한도·HTTPS 구성 |
| 6 | 대표 여행 요청과 기대 결과 정리하기 | 포함/제외/예약 사례 약 20개를 시작점으로 제안 | 한국어 요청→결과 평가와 회귀 검증 |

초기에는 이용자 데이터가 없으므로 ‘인기 순위’를 만들 근거도 없다. 첫 버전은 **운영자 추천**으로 표시하고, 실제 저장·담기 사용량이 쌓이면 기준과 기간을 정해 서비스 내 순위를 추가한다. 위 예시 수량·지역은 합의 전 제안이다.

사용자가 SQL·좌표 변환·임베딩을 직접 할 필요는 없다. 자료를 구할 책임과 사용할 권리, 결과가 좋은지 판단할 담당자를 정하면 개발팀이 시스템에 넣는 절차를 만든다.

## 네이버 연결에서 반드시 구분할 것

- **지도 표시:** 내부 장소의 검증된 좌표를 마커로 표시한다. 기존 내 여행 카드·DAY 레이아웃을 유지하면서 지도 구현을 교체한다.
- **자동차 길찾기:** Directions 5/15로 구간의 이동 거리·시간을 조회한다. 도보·대중교통 시간으로 대체 표시하지 않는다. 이 수단들은 초기 외부 지도 앱 연결 또는 별도 경로 공급자 검토가 필요하다. [Directions 명세](https://api.ncloud-docs.com/docs/application-maps-directions5)
- **업체 검색:** API HUB의 사용자 검색 결과를 제공하는 별도 기능이다. 검색 결과가 조회된다고 내부 업체 DB에 영구 저장하거나 AI에 보낼 권리까지 생기지는 않는다.

현행 Maps 약관에는 반환 좌표의 별도 DB화·재사용 제한이 있고, 2026-09-20 시행 HUB 약관에는 검색 자료의 저장과 AI 입력 제한이 있다. 따라서 **네이버 조회로 업체·좌표를 전량 수집해 RAG에 넣는 안은 기본 구성에서 제외한다.** 내부 DB는 자체 자료·업체 제공·허가된 공공자료로 시작한다. 네이버 자료의 장기 저장이나 AI 활용이 꼭 필요하면 원하는 화면·보관 기간·필드를 적어 별도 허락 범위를 확인한다. [Maps 약관](https://xv-ncloud.pstatic.net/images/provision/%5B%EB%AF%BC%EA%B0%84%5DMaps%EC%84%9C%EB%B9%84%EC%8A%A4%EC%9D%B4%EC%9A%A9%EC%95%BD%EA%B4%80_v0.4_(CLEAN)_1742433558704.pdf), [HUB 약관 개정 공지](https://www.ncloud.com/support/notice/all/2243)

세부 API 주소·키·좌표 형식·호출 한도와 문의할 항목은 [네이버 연결 상세안](NAVER_MAPS_IMPLEMENTATION_20260920.md)에 정리했다. 실제 요금은 신청 시점 콘솔에서 확인하며 지금 월 요금을 확정하지 않았다.

## 개발 순서와 담당자 간 전달 기준

| 순서 | 중심 담당 | 구현 범위 | 다음 작업을 시작할 조건 |
|---|---|---|---|
| 1. 서버 기본 | 백엔드 | 로그인, 권한, DB, 사진 저장, 개발 API 주소 | 두 계정의 데이터가 분리되고 여행 저장/조회 가능 |
| 2. 장소 등록 | 백엔드 + 자료 담당 | 업체/지점 ID, 이름·주소·좌표, 출처, 중복 검수, 자체 추천 기준 | 첫 권역에 식당·숙소를 포함한 검증 자료가 존재 |
| 3. 지도·주변 검색 | 백엔드 + 프론트 | 기존 카드와 마커 연결, 거리 기반 주변 후보, 자동차 경로 | DAY·카드·지도 장소가 같은 ID를 가리킴 |
| 4. AI 간단 생성 | AI + 백엔드 | 기존 Flowise 점검·재사용, 글의 조건 인식, 내부 후보 조회, 완성 일정, 결과 검증 | 챗봇 없이 입력 하나로 서버가 검증한 초안이 기존 화면에 도달 |
| 5. RAG·상세 수정 | AI + 백엔드 + 프론트 | 허가 설명 검색, 결과 상세의 점심 교체/오후 변경/예약 보존, 근거·승인 저장 | 없는 ID·다른 권역·금지 업체·고정 위반을 저장 전 차단. 후보 조립을 강요하지 않음 |
| 6. 앱·운영 검수 | 전원 | Android/iOS, 오류·비용·지연·초안 보존·저장·복구 | 실패해도 기존 여행과 사용자 입력이 보존됨 |
| 향후. 챗봇 추가 | 프론트 + AI + 백엔드 | 대화 화면·이력·세션, 추천/질문/생성/부분 수정 의도 구분. 공통 기능 재사용 | 기존 간단 생성이 유지되고 사용자/여행별 대화 분리·최신 여행 기준 수정 확인 |

프론트 → 백엔드 → AI의 기존 단계 일정은 유지하되, **API 계약과 첫 지역 자료 준비는 앞에서 함께 진행**해야 한다. 백엔드 종료 시 승인된 초기 장소 자료와 읽기 API가 있어야 AI·RAG 4주가 실제 개발 기간이 된다. 1월의 데이터 수집은 확대·보완으로 두고, AI 테스트에 쓸 최초 자료까지 1월로 미루지 않는다.

기준 일정은 프론트 2026-09-15~10-27, 백엔드 5주 10-28~12-01, AI·RAG 4주 12-02~12-29, 2027년 1월 테스트·여행 데이터 수집이다. [기존 일정 원문](FIRST_RELEASE_20_WEEK_BASELINE.md)

기존 기간 변경 없음. 초기 AI·RAG 완료 기준은 **간단 생성의 실제 자연어 인식·검색·초안·검증·저장 연결**. 챗봇 화면과 다중 턴 대화는 해당 완료 기준에서 분리, 향후 일정 별도 산정.

## AI가 실제로 수행할 순서

`간단 생성에 쓴 문장 → 외부 대화·일정 생성 AI가 지역·기간·식사·숙박 의도 인식 → 우리 DB 후보 조회 + 필요 시 외부 임베딩 AI를 이용한 허가 설명 검색 → 같은 생성 AI가 DAY별 방문·식사·숙박 제안 → 우리 서버 검증 → 미리보기 → 상세에서 필요한 부분 수정 → 비공개 저장`

초기 요청의 대화 세션·대화 이력은 필수 항목 아님. 요청 ID·선택 조건·저장 장소·필요 시 여행 버전으로 처리. 불명확한 필수 조건은 같은 입력 화면에서 짧게 확인. 임베딩 AI는 문장을 해석해 일정으로 작성하는 AI와 역할 구분.

모델에게는 후보의 내부 ID와 필요한 사실만 전달한다. 응답은 정해진 구조로 받고, 서버가 ID의 존재·권한·같은 권역·예약 고정·식사 앞뒤 방문·숙박일을 검사한다. 좌표·주소·사진은 모델 응답 대신 DB에서 다시 붙인다. 모델 응답 형식이 맞다는 것만으로 여행 가능성이 검증된 것은 아니다. [구조화 출력](https://developers.openai.com/api/docs/guides/structured-outputs), [함수 호출](https://developers.openai.com/api/docs/guides/function-calling)

자세한 DB 구성·RAG 처리·보관·운영 한도·인수인계는 [AI·RAG 상세안](AI_RAG_IMPLEMENTATION_20260920.md)을 따른다.

## 이번 로컬 수정 범위

- 요청 내용에 따른 식사·카페·숙박 포함/제외, 예약 숙소 유지.
- 오전·점심·오후·저녁·숙박과 식사의 앞뒤 랜드마크 표시.
- 후보 선택을 강요하지 않는 결과 화면과 명시적인 ‘일정 수정’ 진입.
- 서로 다른 지역의 저장 장소를 한 DAY에 조용히 섞지 않고 여행 지역 확인.

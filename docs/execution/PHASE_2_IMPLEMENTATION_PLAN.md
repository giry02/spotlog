# Spotlog 2차 구현 계획 — 저장한 랜드마크로 쉽게 만드는 내 여행

작성일: 2026-09-15 · 최신 사용자 방향 반영 · 상태: 기획안 / 제품 코드 변경 전

[공통 인수인계](HANDOFF.md) · [기존 기능별 지침](PHASE_2.md) · [1차 백업](PHASE_1_WEEK_1_CHECKPOINT.md)

## 1. 사용자가 정한 핵심 방향

**저장한 랜드마크로 DAY별 동선의 뼈대를 먼저 만들고, 각 랜드마크에서 주변 업체를 추천받거나 검색·등록해 채운다. 내 여행은 내가 편하게 쓰는 일정이고, 여행기는 타인에게 보여주기 위한 콘텐츠다.**

기존 계획은 여행기 글·사진 편집을 2차의 첫 과제로 잡아 이 목적을 충분히 구분하지 못했다. 이번 정정은 문구만 바꾸는 것이 아니라 내 여행의 기본 화면, 업체를 담는 동선, 작성 기능의 위치, 구현 우선순위를 구분하는 기준이다.

| 구분 | 내 여행 | 여행기 |
|---|---|---|
| 목적 | 여행 준비와 현장에서 내 동선을 편하게 사용 | 다른 사람에게 경험·여행 정보를 보여주기 |
| 출발점 | 저장한 랜드마크 선택 | 원할 때 내 여행을 바탕으로 여행기 초안 만들기 또는 기존 여행기 작성 |
| 기본 화면 | DAY별 방문 순서, 랜드마크와 선택한 업체, 지도 | 제목·글·사진·장소 카드가 이어지는 읽기 화면 |
| 주요 행동 | 주변 업체 고르기, 검색·등록, 순서/DAY 변경, 이동 확인 | 이야기·사진 편집, 미리보기, 공개, 카드 댓글 |
| 입력 부담 | 글 없이 완성 가능. 이름 자동 제안, 메모·시간은 필요할 때만 | 공개를 위한 제목·설명·사진을 선택적으로 보완 |
| 공개/반응 | 기본 비공개. 댓글·좋아요를 일정 조작에 섞지 않음 | 사용자가 공개한 여행기에 댓글·좋아요 연결 |
| 관계 | 일정이 바뀌어도 작성·공개한 여행기를 자동으로 변경하지 않음 | 내 여행을 참고하지만 별도의 초안·발행 상태와 작성 내용을 유지 |

여행기 작성은 여행을 끝내야만 할 수 있는 기능으로 제한하지 않는다. 사용자가 원할 때 선택하는 별도 흐름이다. 일정 만들기를 완료하려고 글을 쓰거나 공개 상태를 선택할 필요가 없어야 한다.

## 2. 사용자 흐름 — 뼈대를 만든 뒤 필요한 업체만 채우기

**장소 발견 → 저장 → 저장한 랜드마크로 여행 만들기 → DAY별 랜드마크 배치 → 각 랜드마크 주변 업체 담기 → 지도에서 동선 사용**

위 단계는 개념상 순서다. 업체를 추가할 때마다 처음부터 거치는 여러 페이지짜리 절차를 만들지 않는다.

### A. 저장한 랜드마크로 내 여행 만들기

1. 저장 화면에서 같은 지역의 가고 싶은 랜드마크를 고른다.
2. 기존 여행에 담거나 새 여행을 만든다. 새 여행은 기간을 정하고 시작일은 선택 입력으로 둔다. 제목은 지역·기간으로 제안하고 나중에 바꿀 수 있게 한다.
3. 선택한 랜드마크가 DAY별 동선의 뼈대로 보인다. 일정 전체를 글로 설명하거나 음식점·숙소를 함께 확정하도록 요구하지 않는다.
4. 필요한 장소의 순서와 DAY만 바꾼다. 랜드마크만 담겨 있어도 내 여행이 저장되고 다시 열려야 한다.

초기 배치의 제안 규칙은 당일 여행은 선택 순서, 여러 날은 선택 순서를 유지하며 DAY에 나눈 초안이다. 사용자가 이미 정한 DAY·순서는 우선한다. 나눈 결과를 한 화면에서 확인하고 옮길 수 있게 하며 자동 배치를 최적 동선이나 AI 추천으로 안내하지 않는다. 좌표를 반영한 개선·경로 검증은 별도 로직이며, 첫 사용에 AI/RAG 연결을 필수로 두지 않는다.

기존 여행/DAY 담기·저장 상태·DAY 드래그·장소 사진과 출처는 1차 결과를 재사용한다. 새 선택 화면을 여러 개 덧붙이기 전에 기존 담기 흐름으로 해결한다.

### B. 내 여행에서는 일정 목록을 기본으로 사용

- 상단에는 여행 제목과 DAY 선택을 둔다. 본문은 해당 DAY의 랜드마크와 담은 업체 순서다.
- 각 랜드마크에 진입 버튼 하나인 **‘＋ 주변 업체’**를 둔다.
- 음식점·카페는 선택한 랜드마크 바로 다음의 방문 항목으로 보인다. 랜드마크와 함께 선택한 업체라는 관계는 유지한다.
- 일정 순서 변경, 다른 DAY 이동, 제거는 짧은 항목 메뉴에서 처리한다. 지도는 같은 방문 목록을 보여준다.
- 장소마다 ‘아침·점심·저녁·카페·숙소를 채우세요’ 같은 빈 슬롯을 만들지 않는다. 모든 업체를 채워야 여행을 완성할 수 있는 구조도 만들지 않는다.
- 글·본문 사진 업로드·대표 사진·발행 상태 입력을 기본 일정 화면에 두지 않는다. 개인 메모·고정 시간은 항목 메뉴의 선택 기능으로 둔다.

예시: **DAY 1 · 협재해수욕장 → 선택한 식당 → 오설록**. 처음에는 협재해수욕장과 오설록만 있고, 협재해수욕장에서 식당을 고르면 그 사이에 들어간다.

### C. 주변 업체 하단 모달 — 열고 바로 고르기

| 위치 | 제안하는 내용과 동작 |
|---|---|
| 제목 | ‘협재해수욕장 주변’. 현재 기준 랜드마크를 명확히 표시 |
| 종류 | 맛집 · 카페 · 숙소. 처음에는 맛집 목록, 종류를 바꿔도 같은 기준 장소 유지 |
| 검색 | 짧은 ‘업체명 검색’ 입력. 별도 검색 페이지로 이동하지 않음 |
| 첫 목록 | 검색어 없이도 해당 종류의 주변 추천 후보를 바로 표시 |
| 후보 카드 | 사진, 업체명, 종류, 확인 가능한 거리, 짧은 선택 근거, ‘담기’ |
| 상세 | 사진·주소 등 더 보고 싶을 때 선택. 같은 모달 내부 상세로 전환하고 돌아오면 검색/목록 위치 유지 |
| 보조 진입 | ‘저장한 장소에서 고르기’. 찾는 곳이 없으면 ‘직접 등록’ |
| 담은 결과 | 해당 랜드마크 다음에 업체 추가 → 모달 닫기 → 추가된 항목과 취소 안내 |

**기본 업체 추가는 ‘＋ 주변 업체 → 후보의 담기’로 끝난다.** 후보 상세 열람은 선택 사항이다. ‘추천/검색/직접 입력 중 고르기’ 화면을 먼저 통과하게 하지 않는다. 여행·지역·DAY·기준 랜드마크는 현재 화면에서 이어받으며 반복 선택시키지 않는다.

- 첫 후보는 가깝고 현재 종류에 맞는 내부 장소를 제시한다. 자체 순위가 연결되면 그 근거를 함께 반영한다. AI 설명이 준비될 때까지 기본 목록을 막지 않는다.
- 거리만 확인했다면 ‘가까운 곳’으로 안내하고, 가짜 별점·후기 수·근거 없는 인기 순위를 만들지 않는다.
- 직선거리와 실제 이동거리를 구분한다. 좌표 없는 업체에는 거리 숫자를 만들지 않는다.
- 같은 기준 랜드마크에 이미 담긴 업체는 ‘담김’으로 보인다. 다른 DAY에서의 재방문은 가능하다.
- 후보 없음/실패 시 같은 모달에서 검색·저장한 장소·직접 등록으로 이어간다. 빈 결과가 일정을 못 만드는 이유가 되어서는 안 된다.
- 닫기·뒤로가기는 일정에 변화가 없다. ‘담기’가 사용자의 확정 행동이며 불필요한 재확인 팝업을 추가하지 않는다.
- 목록 요청 중 DAY나 기준 장소가 바뀌거나 삭제되면 이전 응답을 잘못 추가하지 않는다.

### D. 내가 아는 업체를 검색하거나 직접 등록

**검색어 입력 → 결과에서 선택 → 담기**가 기본이다. 검색어와 지역 문맥은 모달이 유지한다.

직접 등록은 결과가 없거나 내가 아는 곳을 넣을 때 사용한다. 기본 입력은 **업체명과 주소 또는 지도에서 확인한 위치**로 제안한다. 종류는 앞서 고른 맛집/카페/숙소를 이어받고, 사진·메모·이용 시간은 선택 입력이다. 업체 정보 전체를 작성하는 등록 양식을 먼저 보여주지 않는다.

- 기존 내부 업체와 연결되면 같은 장소 ID를 사용하되, 이름만 같다는 이유로 다른 지점을 합치지 않는다.
- 직접 입력은 우선 **내 여행에 쓰는 장소**를 만든다. 검수된 공용 업체 DB 등록이나 전국 추천 대상으로 자동 공개하는 행동이 아니다.
- 위치를 아직 확인하지 못했어도 일정에 ‘위치 미확인’으로 보관할 수 있다. 지도 핀·거리·이동 시간은 위치 확인 후 연결한다.
- 외부 검색 결과는 이용 범위가 확인된 정보만 담을 수 있게 한다. 허용 전에는 원문 확인과 내부 자료·개인 입력의 담기를 구분한다.
- 추가 후 다시 동일한 여행·DAY를 묻지 않고 원래 기준 랜드마크로 돌아온다.

### E. 숙소는 숙박일에 한 번 연결

주변 업체 모달의 숙소 목록도 현재 랜드마크 주변에서 출발한다. 다만 담은 숙소는 DAY의 숙박 거점으로 표시한다.

- 기본 숙박일을 현재 DAY의 밤으로 제안하고 짧게 표시한다. 매 랜드마크마다 숙소 입력을 반복하지 않는다.
- 이미 해당 밤에 숙소가 있으면 중복 추가 대신 기존 숙소 유지/교체를 선택한다. 다른 날 숙소까지 바꾸지 않는다.
- 연박·이미 예약한 숙소 고정은 숙소를 선택한 뒤 필요한 사람만 사용한다.
- 당일 여행과 마지막 DAY에 숙박을 강제하지 않는다. 추가 숙박이 필요한 경우에만 기간/숙박일을 명시적으로 변경한다.
- 예약 완료 표시는 사용자가 지정한 일정 조건이다. 실제 객실 예약·결제·가격 비교를 뜻하지 않는다.

### F. 업체까지 담은 동선을 편하게 사용

랜드마크와 업체를 담은 목록에서 순서를 바꾸고 DAY를 옮기며 지도에서 같은 방문을 확인한다. 음식점 하나 추가할 때 여행기 편집기를 열지 않는다.

랜드마크를 이동할 때 연결 업체도 함께 이동하는 것을 기본 제안으로 한다. 예를 들어 ‘협재해수욕장과 담은 업체 2곳’이라는 범위를 이동 메뉴에 표시한다. 업체만 별도로 옮길 수 있으며 이 경우 새 기준 방문에 연결하거나 독립 방문으로 바꾼다. 연결이 모호한 상태로 다른 랜드마크 밑에 붙이지 않는다.

랜드마크 제거 시 연결 업체도 제거할지, 업체를 일정에 남길지 같은 메뉴에서 분명히 선택한다. 일반 담기에는 확인을 늘리지 않고, 기록을 함께 지우는 행동에는 영향 범위를 보여준다. 순서 변경 후 자동 저장·마지막 변경 취소가 일정 화면 안에서 동작한다.

## 3. 여행기는 별도 작성 흐름으로 유지

**내 여행 → 원할 때 ‘여행기로 남기기’ → 공개용 초안 → 글·사진 보완 → 미리보기 → 공개**

- 기본 일정 화면에서 글 작성을 요구하지 않는다. 여행기의 기존 작성·사진·본문 카드 기능은 이 별도 진입에 둔다.
- 여행기 초안을 만들 때 DAY·랜드마크·선택한 업체를 기본 자료로 가져온다. 출처·원문 작성자 정보는 보존한다.
- 개인 메모·예약 관련 개인 정보는 자동으로 공개용 초안에 포함하지 않는다. 필요한 내용을 사용자가 선택적으로 옮긴다.
- 여행기 초안 생성/미리보기는 공개가 아니다. 작성본과 발행본을 구분하고 명시적 공개 행동을 둔다.
- 이후 내 여행의 업체·순서를 바꿔도 이미 쓴 글이나 공개 여행기를 자동으로 덮어쓰지 않는다. 공개를 되돌려도 내 일정이 삭제되지 않는다.
- 카드별 좋아요·댓글·답글은 여행기 속 해당 카드에 붙인다. 내 일정의 장소 선택/등록 화면에는 붙이지 않는다.
- 타인의 여행기를 내 여행으로 가져오는 경우에는 DAY·장소 동선을 개인 일정으로 가져온다. 타인의 긴 본문을 내 여행의 필수 편집 내용으로 만들거나 댓글을 복사하지 않는다.

이 구분은 여행기 기능 폐기가 아니다. 2차에서 **개인 일정의 핵심 흐름을 먼저 완성하고**, 기존 글·사진 작성·미리보기·카드 소통은 공개용 여행기 흐름에서 이어 구현한다.

## 4. 변경한 2차 구현 순서

| 순서 | 기능 묶음 | 완료 시 가능한 사용자 행동 | 기존 지침 대응 |
|---|---|---|---|
| 1 | 저장 → 내 여행 뼈대 | 저장한 랜드마크만 골라 DAY별 일정을 만들고 글 없이 다시 열기 | 1차 담기 재사용, P2-01·02·05의 일정 관계/저장 |
| 2 | 랜드마크 주변 업체 모달 | 주변 후보를 바로 보고 담기, 기준 여행·DAY·랜드마크 자동 유지 | P2-08 |
| 3 | 검색·직접 등록·숙소 | 원하는 업체 검색/등록, 숙박일별 숙소 선택·교체·연박 | P2-08·09 |
| 4 | 동선 조정·지도·복구 | 장소 순서/DAY 변경, 지도↔목록 선택, 복사·자동 저장·삭제 취소 | P2-02·05~07·13 |
| 5 | 공개용 여행기 작성 | 내 여행을 바탕으로 별도 글·사진 초안과 미리보기 만들기 | P2-03·04·14 |
| 6 | 여행기 카드별 소통 | 공개용 카드별 좋아요·댓글·답글, 전체 댓글과 분리 | P2-10~12 |

각 기능에 필요한 흐름 결정·검증·수정을 포함한다. 일정표에 별도 기획/설계/고객 수정 공정을 추가하지 않는다. P2-15~16의 검증·인계 조건은 각 묶음의 완료 조건으로 적용한다.

**첫 구현/시연은 1→2를 연결한 한 흐름**이다. ‘랜드마크 두 곳 저장 → 내 여행 생성 → 첫 랜드마크 주변 식당 담기 → 다음 랜드마크와 연결된 일정 확인’을 먼저 완성한다. 광범위한 여행기 편집 기능부터 보완하면서 주변 업체 흐름을 마지막으로 미루지 않는다.

### 고객에게는 2단계로 나눠 보여주기

사용자는 미리 전부 구현해도 괜찮으며 고객에게는 1주 간격으로 나눠 보여주고 싶다고 정함. 따라서 위 여섯 기능 묶음을 **2차의 1단계와 2단계**로 보관한다. 기존 1차/2차/3차 구분을 새로 나누는 의미가 아니다.

| 고객 확인 단계 | 기존 일정 안의 보고 구간 | 고객에게 보여줄 핵심 | 포함 기능 |
|---|---|---|---|
| 2차의 1단계 | 09/30~10/06 · 10/06 화요일 보고 | 저장한 곳으로 여행을 만들고 주변 업체를 쉽게 담는다 | 저장한 랜드마크 선택·DAY 뼈대·글 없는 개인 일정·주변 맛집/카페 하단 모달·담기/제거·기본 순서 조정·자동 저장 |
| 2차의 2단계 | 10/07~10/13 · 10/13 화요일 보고 | 원하는 업체와 숙소를 넣고 실제 사용할 동선을 완성한다 | 같은 모달의 검색/직접 등록/저장한 업체 선택·숙박일/연박·DAY 이동/복사·지도↔목록·변경 취소·별도 여행기 작성/미리보기·카드 소통 |

**1단계 시연:** 협재해수욕장과 오설록 저장 → 내 여행 생성 → 협재해수욕장의 ‘＋ 주변 업체’ → 후보 식당 담기 → ‘협재해수욕장 → 식당 → 오설록’ 확인 → 닫았다 다시 열어 유지 확인. 개인 일정의 글·사진 작성은 요구하지 않는다.

1단계는 업체 담기까지 실제로 작동하는 흐름이다. 2단계 기능의 빈 버튼이나 작동하지 않는 메뉴를 미리 노출하지 않는다. 사용자가 고른 후보는 올바른 랜드마크/DAY에 저장되어야 하고, 모달 취소·추가 실패에서 기존 일정이 유지되어야 한다. 이동/복사/댓글이 사용할 고정 식별자와 데이터 호환은 내부적으로 이 단계부터 준비한다.

**2단계 시연:** 같은 여행에서 원하는 카페 검색 또는 직접 등록 → 해당 밤의 숙소 선택 → 장소 순서/DAY 조정 → 지도 확인 → 복사·취소 확인. 이어서 선택적인 ‘여행기로 남기기’로 글·사진·미리보기·카드 반응을 별도로 보여준다. 여행기 기능을 동선 완성의 필수 단계로 만들지 않는다.

휴지통은 기존 기획의 구체 흐름을 확인한 뒤 2단계의 복구 기능에 연결한다. 아직 확인하지 않은 보관 정책을 완료된 기능으로 보고하지 않는다. 두 단계 모두 현재 프론트 범위이며 실제 네이버·계정별 서버 저장·실사용자 댓글 연결은 기존 후속 백엔드 일정에 둔다.

### 미리 구현하고 단계별 화면을 보관하는 방법

1. 1단계 완료 시점의 코드와 검수 자료를 독립된 체크포인트로 남긴다. 복구 기준과 보여줄 기능 목록을 함께 기록한다.
2. 그 상태를 이어받아 2단계를 구현한다. 사용자 일정 데이터는 이어서 읽을 수 있게 하고 1단계 코드 기준은 변경하지 않는다.
3. 고객에게는 첫 주에 1단계 버전, 다음 주에 2단계 버전을 보여준다. 실제 개발이 먼저 끝나 있어도 이 순서는 유지할 수 있다.
4. 검토용 자료는 단계별로 분리해, 2단계에서 저장한 자료를 예전 1단계 버전으로 열다가 훼손하지 않게 한다. 1단계 자료를 2단계에서 여는 호환은 검수한다.
5. 첫 주에 받은 수정은 후속 버전에 반영하고, 이미 보고한 1단계 원본은 추적 가능하게 보존한다. 1단계 화면의 수정본이 필요하면 새 버전으로 구분한다.

전부 구현한 뒤에도 나눠 보여줄 수 있지만, 개발 중 1단계 상태를 먼저 남기는 방법을 기본으로 한다. 완성본에서 메뉴만 숨기는 것보다 해당 시점에 검증한 화면과 동작을 정확히 다시 보여줄 수 있다. GitHub 백업과 고객 화면 활성화는 별개이며 이번 요청에서는 계획만 보완한다. 실제 커밋·푸시·활성화를 실행한 것은 아니다.

보고 날짜는 기존 목표를 유지하며 실제 완성 상태를 구분한다. 이번 구간의 휴일 제외 가용 평일 8일을 두 단계 전체의 확정 공수로 해석하지 않고, 선행 로컬 구현을 활용한다.

## 6. 자동 저장·복구와 휴지통

- 개인 일정은 장소 추가·순서/DAY 변경 후 자동 저장하고, 글을 작성하고 저장해야만 일정이 남는 구조로 만들지 않는다.
- 여행기 작성은 별도 자동 임시 저장과 미전송 초안 복구를 가진다. 공개 읽기본을 입력 도중 변경하지 않는다.
- 마지막 구조 변경 취소는 해당 내 여행/편집 세션에만 적용하고, 이후 작성한 다른 입력까지 전체 사본으로 덮어쓰지 않는다. 취소 가능 범위·종료 시점을 구현 시 화면 문구와 함께 명시한다.
- 여행 전체 휴지통은 [기존 사용자 흐름 기획안](TRASH_USER_FLOW.md)을 검토한다. 30일·복원 후 비공개·전체 기록만 보관은 아직 제안이다.
- 이번 구분에 따라 **개인 일정 삭제 / 여행기 삭제·공개 해제**가 서로를 자동 삭제하지 않는 원칙을 휴지통 흐름에도 반영한다. 정확한 진입·대상·보관 정책 확인 후 해당 기능을 구현한다.
- 사용자용 JSON 백업/복구나 개발용 계정·데이터 도구를 제품 메뉴에 추가하지 않는다.

## 7. 프론트와 후속 서버의 경계

이번 2차는 추천·검색·등록·담기와 개인 동선을 사용하는 화면/상태를 구현한다. 기존 MapLibre를 유지하며 지도 제공자 교체를 자동 추진하지 않는다. 실제 네이버 API·업체 매칭·계정별 저장·실사용자 댓글은 후속 백엔드 일정에서 연결한다.

- 기본 주변 후보는 사용권을 확보한 내부 자료와 위치·업종으로 제시할 수 있도록 준비한다. 실제 순위가 오면 같은 내부 업체 ID에 연결한다.
- AI/RAG는 추후 근거·취향 추천을 보완한다. 저장→일정 생성→주변 업체 선택의 기본 이용 흐름이 AI 응답에 종속되지 않게 한다.
- 업체 이름과 내부 순위·주소·좌표의 매칭은 데이터 연결 작업으로 분리한다. RAG나 모델 학습을 먼저 해야 지도를 쓸 수 있는 구조로 잡지 않는다.
- 외부 검색은 [데이터 수급·네이버 계획](../DATA_SUPPLY_AND_NAVER_PLAN.md)의 범위를 따른다. 구체 규격과 사용 권한은 실제 연결 전에 공식 문서/계약으로 확인하며, 이번 기획으로 새 사용 권한을 확정하지 않는다.
- 로컬 후보·예시 상태는 실제 사용자 집계나 실시간 검색으로 표시하지 않는다. 실패 상태를 검수하기 위한 도구는 분리된 검수 진입에 둔다.
- 신규 네이버 데이터 수급·AI/RAG 서버·경로 최적화·예약/결제·스토어 출시는 이번 기획의 제품 구현 범위가 아니다.

## 8. 완료 기준

1. 랜드마크만 저장한 사용자가 글·사진·발행 상태를 입력하지 않고 내 여행을 만들 수 있다.
2. ‘＋ 주변 업체’를 누르면 후보가 바로 보이고, 후보의 ‘담기’로 해당 랜드마크 다음에 등록된다. 동일한 여행·DAY·지역을 반복 입력하지 않는다.
3. 검색·직접 등록·저장한 장소 선택 후에도 기준 문맥과 입력/목록 위치가 유지된다. 취소하면 일정이 그대로다.
4. 업체가 없거나 위치가 미확인인 상태도 일정에 표현할 수 있고 가짜 좌표·거리·인기 숫자를 만들지 않는다.
5. 숙소는 해당 숙박일에 연결되며 당일/마지막 DAY의 숙박 강제·연박 중복·다른 날의 의도치 않은 교체가 없다.
6. 랜드마크/업체 이동·복사·제거·취소 후 실제 동선과 지도 번호/선택이 맞고, 다른 여행이나 재방문 기록이 함께 바뀌지 않는다.
7. 업체 하나 추가하거나 동선을 확인하기 위해 여행기 글 편집기를 통과하지 않는다.
8. 여행기 작성/공개는 선택 흐름이며, 개인 일정 수정·삭제와 공개 콘텐츠/반응이 서로 자동 변경되지 않는다. 개인 메모가 자동 공개되지 않는다.

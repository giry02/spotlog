# Spotlog 순차 개발·인수인계·앱 출시 일정안

> **이전 43주 일정:** 첫 오픈 범위를 줄이고 프론트 기획·고객 수정 시간을 반영한 [최신 24주 세부 일정](FIRST_RELEASE_24_WEEK_PLAN.md)을 우선한다. 아래 2027-07-13 목표는 이전 전체 범위 산정 이력이며 최신 첫 오픈 목표가 아니다.

작성일: 2026-09-15 · 상태: 사용자 요청 방식에 따른 일정 제안

**진행 순서: 프론트엔드 완료 → 백엔드·업체 기준정보 완료 → AI·RAG 완료 → 실제 화면/앱 통합·출시 검수.**

프론트 1명·백엔드 1명에 더해 **AI/RAG 전담 1명**을 별도로 배정하는 가정이다. AI와 RAG를 각각 다른 2명에게 나누는 안은 아니다. 주개발을 겹치지 않으며 단계별 완료 조건을 통과한 뒤 다음 담당자가 개발을 시작한다. 공통 규격 설명·인수인계 회의는 가능하되 후속 기능 구현을 미리 병행하는 일정으로 계산하지 않는다.

**기준 일정 43주, 정식 오픈 목표 2027-07-13(화), 예비 2주를 포함한 확인 시점 2027-07-27(화).** 2026-09-15 착수 협의, 주간 작업 산정은 09-16부터 시작한다. 공급자·자료·고객 검수·스토어 승인에 따라 조정할 목표이며 무조건 완료를 약속한 계약일이 아니다.

## 1. 이전 계획에서 달라진 점

- 백엔드가 맡던 RAG·AI·경로 배치·관광 안내·번역을 AI/RAG 전담자에게 옮긴다.
- 모든 차수의 화면을 먼저 완성하고, 이후 실제 서버와 기준정보, 그다음 실제 AI를 만든다.
- 업체의 실제 지점 ID·순위·주소·좌표·원천 자료·갱신/삭제는 백엔드에서 완성한다. AI 담당자는 이 자료를 넘겨받아 검색 색인·모델·추천에 연결한다.
- 프론트 완료는 실제 AI 호출까지 끝났다는 의미가 아니다. 예시 응답으로 모든 화면과 예외 상태를 검수한 상태다.
- 실제 API에 연결하면서 필요한 프론트 수정과 양 OS 검수는 마지막 통합 단계에 따로 배정한다. 앞 담당자가 영구히 빠져도 되는 계약으로 잡지 않는다.
- [이전 병행 일정](COLLABORATIVE_DELIVERY_PLAN.md)의 2027-03-02 목표는 이번 순차 진행안에 적용하지 않는다. 인력 증가가 개발 기간 중첩을 의미하지 않으므로 달력 기간은 길어진다.

기존 1·2·3차는 기능 묶음으로 유지한다. 이번 S1/S2/S3는 직무별 개발 단계다. 따라서 S1에는 기존 1차뿐 아니라 2차·3차의 프론트 화면도 포함된다.

S1→S2, S2→S3는 직전 단계 검수와 인계가 선행 조건이다. 이전 단계가 지연되면 후속 시작일도 순서대로 조정한다. 화면만 완성된 날짜에 서버 완료를 선언하거나, AI의 예시 응답을 실제 추천으로 보고하지 않는다.

### S1 · 프론트 완료의 의미

발견·검색·저장·갤러리·사진 출처, 여행/DAY·편집·복구·사진, 주변 업체·숙소·순위 목록·지도, 댓글/답글·권한 상태, AI 입력/미리보기/승인/부분 변경, 관광 안내·한/영 UI까지 화면을 구현한다. Android/iOS 기본 앱 틀에서 렌더링·키보드·뒤로가기 등 기초 동작을 확인한다.

실제 검색·서버 저장·댓글 집계·AI·번역의 자리는 합의한 예시 응답으로 검수한다. 생성 취소·빈 결과·시간 초과·권한 오류·좌표 없음·오래된 번역 같은 상태를 포함한다. 원래 화면 역할별 디자인을 유지하며 샘플과 실제 연결을 명시한다.

고객이 화면 흐름과 입력 항목을 확인하고, 다음 담당자가 사용할 데이터/오류 규격·업체/방문 ID 구분·API 목록·화면별 예시와 검수 시나리오를 인계하면 S1을 완료한다.

### S2 · 백엔드 완료의 의미

실제 로그인·사용자 권한·여행/사진 저장·동기화·기존 로컬 기록 이전·댓글/좋아요·기본 신고/차단·관리 기능을 구현한다. 검색 API 중계, 키·한도·실패 처리를 포함한다.

업체/지점별 내부 ID, 내부 순위의 대상·지역·업종·집계 시점, 주소·좌표·사진·출처·상태를 연결한다. 동명 업체·지점 혼동·중복·이전·좌표 오류를 검수한다. 원천 자료의 수급·공개 범위·변경/삭제·갱신 경로를 준비한다.

기존 프론트 계약에 맞는 API를 독립 시험하고, 실제 계정·저장·업체 자료를 검수한다. 공용/비공개 자료 구분, 원문 버전·업체 ID·출처·갱신/삭제를 AI 담당자가 사용할 수 있게 제공한다. 최종 앱 전체 연결 검수는 S4에서 수행한다.

### S3 · AI/RAG 완료의 의미

백엔드가 제공한 검수 자료를 업체 ID·권한·원문 버전과 함께 검색 색인에 연결한다. 실제 내부 검색과 모델 API로 지역/취향 추천·저장한 장소 구성의 두 모드를 구현한다.

외부 모델 API를 호출하는 AI 서비스 서버와 검색 저장소의 개발/운영 환경, 키·요청 제한·로그·배포 설정을 포함한다. 자체 GPU에 모델을 설치·운영하거나 모델을 학습하는 서버 구축은 포함하지 않는다.

다일 배치·필수/제외·식사·숙박 DAY·예약 고정, 지원 지역/수단의 실제 경로 검증, 부분 재생성·변경 비교, 관광 안내·실제 번역을 연결한다. 주소·좌표·최신 순위는 모델의 기억이 아니라 백엔드 기준정보에서 조회한다.

자료 부족·권한·취소·오래된 응답·중복 요청·시간·비용과 추천 근거를 검증한 뒤, 요청/응답 규격·평가 자료·실패 예시·운영 설정을 인계한다. 공급자 지원 밖의 경로나 확인되지 않은 정보는 명시적으로 구분한다.

### S4 · 통합·출시 완료의 의미

예시 응답을 실제 서버/AI로 교체하고 입력·저장·권한·오류·번역·지도 선택을 연결한다. 이때 필요한 프론트 연동 수정은 별도 작업량에 포함한다. 새 화면 기능 추가나 전면 재설계와 구분한다.

모바일웹과 Android/iOS에서 실제 로그인·사진·지도·AI·키보드·뒤로가기·재실행을 확인한다. 06/15 베타 시작, 06/29 출시 후보 검수, 07/06 스토어 제출, 07/13 조건부 공개를 목표로 한다. 스토어 승인과 실제 설치 가능 여부를 구분해 보고한다.

## 5. 업체 기준정보와 RAG 인수인계

주안반점 사례에서 다음 항목이 연결되어야 한다.

1. 실제 매장/지점을 구분하는 내부 업체 ID. 기존 placeId로 충분하면 중복 ID를 새로 만들지 않는다.
2. 업체 ID에 연결된 순위·지역·업종·집계 시점과 검수된 주소·좌표.
3. 설명·사진·원문에 연결된 업체 ID·출처·공개 권한·버전·확인일.
4. 변경·이전·폐업·비공개·삭제 시 기준정보와 검색 자료를 갱신하는 방법.
5. AI가 선택한 업체 ID로 현재 주소·좌표·순위를 조회하는 API.

**S2 백엔드:** 기준정보와 실제 지점의 일치를 검수하고 이를 제공한다. **S3 AI/RAG:** 해당 ID와 권한을 자료에 연결해 색인·검색·추천을 수행한다. 네이버 자료를 그대로 RAG에 수집하는 작업으로 해석하지 않는다.

초기 공개 지역 최대 3곳, 장소/업체 합계 약 100~200건이라는 이전 산정 전제를 유지한다. 실제 대표 업체 50~100건의 ID·주소·좌표·지점 구분·중복 현황을 확인해 수량을 확정한다. 기존 순위 서버/API가 준비돼 있는지는 실제 자료로 확인하며 예시만으로 이미 구현됐다고 간주하지 않는다.

고객 측 원천 자료·순위 기준·개발자 계정·API 신청 준비는 행정/자료 준비로 미리 할 수 있다. 이를 백엔드나 AI 기능 구현을 먼저 시작한 것으로 집계하지 않는다.

## 6. 화요일 보고 일정

모든 주차는 화요일 보고를 기준으로 유지한다. 초기에는 화면 시연, 중간에는 실제 API·업체 자료 검수, 후반에는 실제 AI와 앱 베타를 보고한다. 새 기능이 없는 주에도 인수인계·검수·자료 오류·수정 결과를 보고한다.

고객에게 보여줄 버전은 검수가 끝난 Git 커밋 또는 태그로 고정하고, 해당 버전의 시연 주소·변경 내용·샘플/실제 연결 상태를 함께 기록한다. 후속 개발은 별도 작업 브랜치에서 진행해 고객 검토 중인 버전이 바뀌지 않게 한다. 서버 단계에는 API 검수 결과와 업체 표본을 함께 제시하며, 모든 보고에서 새 화면이 추가되는 것으로 약속하지 않는다.

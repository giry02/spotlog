## 기본 방향

간단 입력 → 맥미니 소형 LLM 조건 해석 → 서버 조건 검증 → 우리 DB·RAG 조회 → 우리 서버의 일정 구성·계산 → 소형 모델 설명 → 서버 검증 → 초안 확인·저장. 직접 선택값·원문·추가 요구 보존. Jev는 별도 비교 후보로 두며 RAG 검색 기능으로 취급하지 않음.

소형 모델이 해결하지 못한 부분 중, 필요한 입력·근거가 충분하고 모델의 해석·표현 문제로 판정된 부분만 대형 LLM에 전달. 이미 검증된 조건·일정·예약은 고정. 두 모델 모두 같은 허용 후보·DB·RAG 근거 사용. 대형 모델의 결과도 같은 기준으로 재검증.

초기에는 기존 AI 간단 생성과 ‘저장 장소로 추천’ 유지. 챗봇은 향후 같은 처리 기능을 호출하는 별도 진입점으로 추가.

## 구성별 역할과 위치

| 구성 | 역할 | 내부·외부·준비 상태 |
|---|---|---|
| Spotlog 화면 | 간단 요청·초안 확인·선택 수정·저장 | 우리 화면, 기존 시제품 |
| Spotlog 서버 | 인증·조건 검증·후보 조회·일정 계산·대형 호출 판정·최종 검증·저장 | 우리 서버, 신규 구축 |
| 외부 Jev | 고정 항목 분류의 선택 비교 후보. RAG 직접 검색 아님 | 기본 흐름에 필수 아님. 한국어·속도 시험 전 |
| 소형 언어 모델 | 기본 조건 해석·근거 기반 설명 | 맥미니 Qwen3.5 4B/9B 로컬 평가, 채택·설치 전 |
| 대형 LLM | 실패한 조건·DAY·방문·설명만 보완 | 외부 모델 API. 제공자·모델 미선정, 조건부 호출 |
| Flowise | 서버의 처리 경로 판정에 따라 모델·조회 도구 실행 | 맥미니 기존 설치. Spotlog 연결·운영 검증 필요 |
| 임베딩 AI | 허가 설명·검색문을 의미 검색용 숫자로 변환 | 맥미니 Qwen3 Embedding 0.6B 로컬 우선 시험안 |
| DB·RAG | 실제 ID·좌표·순위·예약·허가 설명 근거 제공 | 우리 DB, 신규 구축. RAG는 검색·근거 제공 방식 |
| 네이버 Maps 등 | 지원 범위의 주소·지도·경로 정보 | 외부 서비스. 실패 시 미확인 표시, AI로 수치 생성 금지 |

Flowise가 설치돼 있다는 사실과 맥미니에서 소형 모델을 구동할 수 있다는 판단은 별개. 장비·한국어 품질·동시 처리·운영 안정성 평가 후 배치 선택. AICC는 서비스 유형이며 모델 크기를 뜻하지 않음. Jev 선행 판별 구성과 로컬 단독 해석을 같은 한국어 요청으로 비교. Jev가 기존 LLM 작업을 줄일 때만 속도 개선 기대.

## 대형 모델 호출 기준

| 상황 | 처리 |
|---|---|
| 지역·기간 등 핵심 입력이 실제로 없음 | 기존 입력 필드에서 확인. 대형 호출 없이 보완 |
| 복합 요구·모호한 조건 | 원문·선택값·추가 요구를 소형 LLM으로 해석 → 서버 검증. 실제 없는 정보는 고객 확인 |
| 입력은 충분하나 소형이 복잡한 포함·제외 조건을 잘못 해석 | 미해결 필드·원문·검증 실패 사유만 대형에 전달 |
| 소형 출력 형식 오류 | 서버 형식 검사·제한된 기본 복구 후, 근거 충분·호출 한도 유효할 때 해당 부분만 대형 보완 |
| 후보·근거가 충분하지만 설명이 요청과 모순되거나 근거 밖 표현 포함 | 실패한 설명과 허용 근거만 전달. 재검증 전 공개·저장 금지 |
| 등록된 업체·설명·좌표가 없음 | 미확인·후보 부족 표시, 추가 입력·자료 보완. 대형으로 업체·좌표 생성 금지 |
| 지도·DB·Flowise·로컬 AI 연결 실패 | 원인별 재시도·기존 초안 유지. 대형 호출로 장애 우회하지 않음 |
| 이동 시간 계산 오류·서버 일정 조합 오류 | 서버 계산·구성 로직 보정. 대형 모델을 계산 엔진 대체로 사용하지 않음 |
| 시간·거리·예약 조건상 불가능한 일정 | 충돌 조건 안내·수정 요청. 대형이 해결했다고 간주하지 않음 |
| 대형 보완도 검증 실패 | 검증된 부분만 제시·해당 항목 보류·추가 확인. 연속 대형 재호출 없음 |

대형 필요 여부는 서버의 형식·ID·제약·근거 검사 결과와 오류 분류로 판정. 모델의 자기 확신 점수만으로 결정하지 않음. 의미 검증은 완전 자동 보장 영역이 아니므로 실제 한국어 요청 평가집으로 누락·오판 측정. RAG 연결만으로 사실 오류가 자동 제거되는 구조 아님.

## 대형에 전달할 정보

- 요청 ID·기존 초안 버전·수정 대상 필드/DAY/visitId
- 해당 부분에 필요한 원문 요청·확정 조건·허용 후보 ID·허가된 근거
- 검증 실패 코드·충돌 내용·변경 가능한 범위
- 유지할 일정·예약·고정 장소와 앞뒤 방문 맥락
- 응답 형식: 변경 제안만 반환, 임의 ID·새 업체·없는 사실 추가 금지

서버에서 허용된 변경 범위인지 확인 → 변경 부분 검증 → 지역·순서·예약 등 전체 영향 검증 → 최신 버전에 병합. 오래된 버전이면 자동 덮어쓰기 없이 최신 일정 기준 재확인. 사용자 확인 전 확정 저장 없음.

## 초기 운영 정책 제안

- 요청 전체에서 대형 호출 최대 1회. 입력 보완에 사용했다면 같은 요청의 결과 보완에서 다시 호출하지 않음
- 소형·대형별 시간·토큰·비용 상한 설정. 숫자는 실제 품질·지연·비용 측정 후 확정
- 호출 사유·검증 실패·보완 성공·총 지연·비용 기록. 무조건 대형으로 흘러가는지 점검
- 전체 일정 재생성 대신 미해결 부분만 처리. 나머지는 원본과 비교해 보존 확인
- 외부 모델 전송 자료의 허용 범위·필요 최소 정보 준수
- 모델 선택은 한국어 조건 인식·구조화 출력·근거 준수·부분 수정 평가 후 확정

위 정책은 구현 기준 제안. 비용 절감률·대형 전환율·응답 시간 확정치 아님.

## 예시

“부산 2박 3일, 맛집 포함, 숙소 제외” → 소형 LLM 조건 해석 + 서버 검증 + 우리 DB·RAG 검색 + 서버 일정 구성 + 소형 설명으로 완료하는 설계안. 실측 응답 예시 아님.

“둘째 날은 해산물 제외, 첫날 예약은 유지하고 점심만 바꿔줘” → 소형 결과에서 둘째 날 제외 조건만 누락된 경우 해당 조건·DAY·후보만 대형에 전달. 첫날 예약과 다른 DAY는 유지. 대형 결과도 서버에서 검증.

“등록되지 않은 지역의 식당 추천” → 데이터 부족 안내. 대형의 외부 지식으로 식당을 만들어 넣지 않음.

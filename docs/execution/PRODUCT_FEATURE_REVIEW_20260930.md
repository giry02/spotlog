# Spotlog 추가 기능 기획 검토

2026-09-30 기준. 프론트·DTO 구현 작업과 별도로, 최신 통합 로컬 소스와 기존 기획·검수 보고서를 읽어 추가 기능을 검토한 보고서. 이번 검토는 기능 제안이며 소스 구현 지시나 공개 범위 변경이 아님.

지금 추가할 가치가 큰 기능은 만든 여행을 현장에서 이어 쓰고, 필요한 장소만 쉽게 바꾸는 기능. 생성 단계의 입력을 늘리기보다 기존 내 여행 카드·장소 메뉴·주변 업체 하단 팝업을 활용하는 방향을 권장.

## 먼저 권장하는 세 가지 기능

### 1 방문 완료와 다음 장소 이어가기

예시: 해운대해수욕장 방문 → 완료 표시 → 다음 식당을 바로 확인 → 길찾기. 네이버 지도에서 돌아오거나 앱을 다시 열어도 같은 DAY와 진행 위치를 이어서 확인.

- 진입은 내 여행의 기존 카드 메뉴에서 시작. 여행 중에는 간단한 현재/다음 장소 요약을 사용하되 큰 화면·상단 메뉴를 새로 만들지 않음.
- 미방문·완료·건너뛰기를 구분. 완료 취소와 건너뛰기 취소 제공. 장소를 일정에서 삭제하는 행동과 구분.
- 완료된 카드도 기존 방문 순서에 유지. 다음 미방문 장소를 기본 제안하되 사용자가 다른 장소를 선택할 수 있게 함.
- 날짜 미정 여행은 오늘의 DAY를 추측하지 않고 마지막 선택 DAY를 유지. 출발 날짜가 있으면 해당 DAY를 제안하는 정도로 제한.
- 위치 권한이나 GPS가 없어도 사용 가능. 자동 도착 판정·상시 위치 추적은 후속 검토.

프론트에서 가능한 부분: 진행 표시·되돌리기·다음 장소·같은 기기 재접속 복원. 서버 필요 부분: 계정별 기기 간 동기화.

데이터 기준: 실제 방문 상태는 공용 장소의 속성이 아니라 `tripId + visitId`에 귀속. 같은 장소를 다른 DAY에 재방문하면 별도 기록. 일정·DAY 복사 시 완료 기록은 초기화.

현재 여행 안내에는 선택 장소 다음 순번을 알려주는 기능이 있으나 실제 방문 상태 모델은 확인되지 않음. 09/26 제안의 필요성을 이번 소스 검토에서도 재확인.

### 2 음식점과 카페 한 곳만 교체하기

예시: 동백섬 뒤 점심 식당이 마음에 들지 않음 → 해당 식당의 ‘다른 곳으로 교체’ → 현재 랜드마크·점심 시간대에 맞는 후보 → 선택 → 나머지 일정 유지.

- 기존 주변 업체 하단 팝업을 재사용. 여행·DAY·지역을 다시 묻지 않음.
- 앞뒤 방문과 기준 랜드마크를 유지하고 해당 자리의 업체만 변경. 식당을 삭제한 뒤 새로 담는 반복을 줄임.
- 같은 종류·같은 권역의 후보를 먼저 표시. 현재 업체·이미 담은 업체의 상태를 표시하고 중복을 방지.
- 장소 관련 메모·예약은 새 업체로 무조건 복사하지 않음. 시간대처럼 유지할 값과 장소에 종속된 값을 구분.
- 확인 전에는 원래 일정 유지. 교체 후 마지막 변경 취소 제공.
- 예약 고정 숙소는 현재 보호 규칙을 따르는 별도 교체 흐름 유지.

프론트에서 가능한 부분: 내부 후보 목록·같은 자리 교체·변경 취소·실패 시 원본 유지. 서버/AI 필요 부분: 실제 경로에 맞는 추천·최신 영업 정보·문장으로 교체 요청.

현재 숙소 교체는 존재하지만 음식점·카페의 같은 자리 교체는 별도 기능으로 확인되지 않음. 기존 AI 부분 수정 샘플은 주로 방문 제외·방문 수 줄이기이므로 대체 업체 추천과 구분.

### 3 일정 경고에서 바로 수정하기

예시: 점심 뒤 다음 장소까지 이동 시간이 부족함 → 해당 연결 구간 표시 → ‘방문 시간 바꾸기’, ‘이 장소 다른 DAY로’ 또는 ‘더 가까운 곳으로 교체’ → 바뀐 부분 확인.

- 새 경고 화면을 늘리지 않고 기존 DAY 지도·일정의 해당 구간에서 진입.
- 확인된 충돌과 이동/영업 정보 미확인을 구분. 추정 계산으로 실제 가능 여부를 확정하지 않음.
- 여행 전체를 다시 만들기보다 해당 방문·연결 구간만 수정하는 행동을 먼저 제공.
- 기존 방문 시각 수정·DAY 이동·부분 수정 기능을 활용. 필요한 경우 체류시간을 선택적으로 편집할 수 있게 연결.
- 실제 도보·대중교통 경로가 없으면 자동차 시간으로 대체해 검증 완료라고 표시하지 않음.

프론트에서 가능한 부분: 경고와 관련 방문 연결·수정 진입·변경 범위 비교. 서버 필요 부분: 실제 경로·이동 시간·운영 일정 검증.

현재 지도에는 추정 시간과 충돌 안내가 있으므로 이번 제안의 신규 부분은 ‘경고 → 해당 항목 수정’의 연결.

로컬 저장 기능이 있다는 사실은 오프라인 앱 구동·사진·지도·최신 정보 이용을 보장하지 않음. 5번은 읽기 기능부터 검토하고 지도·실시간 검색은 연결 복구 후 사용.

여행 링크를 받은 동행자가 편집하는 공동 작업은 6번의 최소 범위에서 제외. 우선 읽기 전용 공유 후 실제 사용을 보고 판단.

## 현재 일정에 넣는 방식

기획 판단상 1·2번을 첫 보완 묶음으로 권장. 현장에서 바로 쓸 수 있고 기존 카드·팝업을 재사용할 수 있음. 3번은 진행 중인 프론트·DTO 정비와 맞물려 경고 데이터의 형태와 수정 진입을 먼저 정리하면 좋음.

4번은 화면 수를 늘리기보다 후보를 채우는 데이터 작업으로 진행. 한 권역의 랜드마크·식당·카페·숙소가 연결되는 시연 단위를 먼저 갖추고 지역을 늘림. 수집 확인 전 실제 가격·영업시간·접근성 사실을 표시하지 않음.

5~7번은 서버 계약과 운영 정책까지 필요한 기능. 기존 확정 일정을 이 보고서만으로 변경하지 않음. 구현 공수는 실제 DTO·저장·검수 범위 결정 후 산정.

지금 구현 중인 핵심 DTO에 모든 제안을 필수 필드로 넣기보다 후속 계약으로 나눠 합의하는 편을 권장.

## 이후로 미룰 확장

실시간 공동 편집, 예약·결제·가격 비교, 자동 위치 추적·도착 판정, 자동 날씨 대체 일정, 챗봇을 통한 전체 대화 수정, 대규모 추천 랭킹 확장은 후속 검토. 지금의 저장→간단 생성→내 여행 사용 흐름을 먼저 완성하는 편을 권장.

특히 비·휴무 대안은 유용하지만 현재 영업·날씨·실내외 근거가 부족한 상태에서 자동 판단을 약속하면 기능의 신뢰가 떨어짐. 먼저 2번의 사용자 선택 교체와 4번의 검증된 정보를 갖추고 확장.

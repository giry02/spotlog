## 1. 이번 산출물과 사용 방법

기존 전체 개발·AI·데이터 수급 계획을 1·2·3차 실행 지침과 기능별 엑셀 일정으로 구체화함. 이번 작업은 **문서와 일정표 제작**이며 서비스 기능을 추가 구현하거나 공개 배포한 작업이 아님.

- [1차 실행 계획](PHASE_1.md): 발견·저장·정확한 여행/DAY 담기·사진 카드 갤러리·홈 AI 로컬 초안.
- [2차 실행 계획](PHASE_2.md): 초안 복구·편집·이동/복사·주변 음식점/숙소·카드별 좋아요/댓글/답글·지도.
- [3차 실행 계획](PHASE_3.md): 추천 조건·내부 후보·승인·부분 재생성·관광 안내·영어 보기·샘플 연결 계약.
- [기능별 Excel 일정](../../outputs/01a00d5a-887a-70b2-93cf-260846464314/Spotlog_차수별_개발일정_20260915.xlsx): 시작일·작업일 수정, 차수별 요약·기능별 일정·완료 조건·주간 일정·휴일/출처.

새 대화에서는 이 파일과 구현할 차수 MD를 함께 읽음. **문서 열람만으로 구현이 승인된 것은 아님.** 사용자가 해당 차수 구현을 요청하면 아래 절차를 따름. 차수별 MD 마지막에 바로 붙여 넣을 요청문을 제공함. 별도 새 대화 생성이나 다른 작업에 메시지 전송은 이번 요청에 포함하지 않음.

자료가 없는 새 환경에서는 이 네 MD만으로 기존 프로젝트 전체를 복원할 수 없음. 실제 로컬 변경 파일과 필요한 자산도 안전하게 전달받아야 함. GitHub 소스만 내려받으면 현재 로컬 미공개 작업까지 포함되는 것이 아님.

## 5. 변경하면 안 되는 제품 결정

### 저장과 내 여행

- 저장은 마음에 든 장소를 모으는 목록임. 불필요한 ‘보관함 안의 분류 안의 여행’ 계층을 추가하지 않음.
- 저장 화면에는 모으기·담기·만들기·AI 진입을 제공함. 여행 편집기를 저장 본문에 펼치지 않음.
- 담기는 기존 하단 팝업에서 장소 카드와 여행·기간·DAY를 확인함. 확정하면 해당 내 여행 DAY 상세로 이동함.
- 새 여행 생성은 저장에서 시작할 수 있음. 생성 후 이름·기간·DAY·순서·내용 관리는 내 여행에서 함.
- 기간 2일과 담을 DAY 2는 별개 상태임. 여행 기간 버튼을 DAY 선택처럼 재사용하지 않음.
- 북마크 해제와 여행 내 방문 해제는 별개임. 다른 DAY 재방문을 허용하고, 같은 DAY 중복은 차단함.

### 화면과 디자인

- 기준은 현재 승인된 **전체 화면의 역할별 디자인**임. Saved 하나를 모든 화면의 템플릿으로 사용하지 않음.
- `SavedPlaceCard`: 작은 가로 저장 카드. `LandmarkGuideCard`: 큰 세로 발견 카드. 여행기 본문 임베드·전체 화면 미디어는 별도 역할임.
- 지역 안내·AI 미리보기·담기 팝업은 큰 카드의 사진·정보 위계를 재사용함. 저장 본문의 가로 카드를 크게 바꾸지 않음.
- 스타일 가이드를 핑계로 폰트·간격·모서리·색상·버튼을 전면 통일하지 않음. `styles.css`와 승인된 역할별 CSS를 우선하며 `theme.css`·`ui.tsx`의 기본값으로 교체하지 않음.
- 신규/변경 글자는 STYLE_GUIDE §3 역할 계약을 적용함. 과거의 8~10px 정보 글자를 새 기본값으로 복제하거나 작은 화면에서 글자를 줄이지 않음.
- 기존 사진 높이·여백 안에서 가로 사진 탐색을 넣음. 자동재생·무한 반복·별도 새로운 시각 유형을 임의 추가하지 않음.
- 하단 팝업의 닫기·뒤로가기·키보드·포커스와 미전송 글을 보존함. 출처는 같은 패널 안에서 확인하고 돌아오며 팝업을 중첩하지 않음.

### 스팟·주변 업체·소통

- 스팟을 먼저 골라 일정 기본 구성을 잡고 음식점·카페와 숙박 거점을 보완함. 이 순서만으로 실제 동선이 보장되는 것은 아님.
- 내 여행의 ‘+ 주변 장소’는 여행·DAY·기준 방문을 이어받음. 추가한 음식점은 기준 스팟 다음, 숙소는 숙박 DAY의 거점으로 연결함.
- 카드별 좋아요·댓글·답글은 **여행기 ID + 카드 ID**를 대상으로 함. 업체 전체 리뷰나 여행기 전체 댓글과 섞지 않음.
- 좋아요 버튼은 토글, 좋아요/댓글 숫자는 해당 하단 팝업을 엶. 답글은 같은 팝업에서 펼치고 작성함.
- 카드 이동은 ID와 반응 유지, 복사는 새 ID와 반응 0건임. 댓글 수는 공개 댓글·답글 합계임.

### 데이터·AI·외부 서비스

- 한국어 원본을 유지하고 번역본을 버전으로 연결함. 국내 콘텐츠를 외국인용 콘텐츠로 대체하지 않음.
- 사용권 있는 공공·직접 제작·제휴·사용자 자료를 내부 추천에 활용함. 비공개 여행과 허용되지 않은 자료를 공용 RAG에 넣지 않음.
- TourAPI 무료 제공과 개별 사진의 이용 조건은 다름. 사진·좌표·출처·권리는 자산별 검수함. ‘저작권 없음’으로 표시하지 않음.
- 사진 설명과 출처 메타를 분리하고 ‘사진 출처’ 버튼/하단 상세를 유지함. 복사·번역·사진 전환 시 저작자·원문·라이선스를 보존함. 버튼만 있으면 모든 사용 조건을 충족한다고 보장하지 않음.
- 네이버는 별도 외부 검색 후보임. 신규 API HUB 계약·쿼터·표시·보관·재정렬·AI 입력 허용을 연결 전에 재확인함. 결과를 자동으로 내부 DB·RAG에 넣지 않음.
- 실제 추천은 내부 후보 검색/인기·메타 필터, 경로/시간 검증, 설명 모델을 분리하는 후속 방향임. OR-Tools만으로 인기 장소 추천을 대신하지 않음. 모델 공급자·버전은 계약과 평가 후 선택하며 특정 GPT 모델로 고정하지 않음.
- 1~3차에서는 샘플 연결부를 검증함. 실제 RAG·LLM·경로·번역·로그인·커뮤니티 집계가 동작하는 것처럼 표시하지 않음.

## 7. 차수 간 데이터 계약

새 DB를 만드는 지시가 아니라 기존 필드를 확인해 부족한 표현만 보완하는 최소 논리 계약임.

| 개념 | 구분·보존할 내용 |
|---|---|
| 장소 | 내부 placeId, 원천 ID, 이름·주소·좌표, 검수·권한·출처 |
| 사진 | mediaId, placeId, 이미지·순서·설명·대체 텍스트, 자산별 사용 조건 |
| 여행 방문 | visitId, placeId, journeyId, 안정된 DAY 식별, 순서·체류·필수·고정 시간 |
| 본문 카드·블록 | cardId/blockId와 방문 연결, 글·사진·장소 순서. 이동 유지·복사 재발급 |
| 주변 업체·숙소 | 기준 visitId 또는 숙박 DAY 연결. 예약·연박·삭제 후 관계 유지 |
| 반응·댓글 | journeyId+cardId, 샘플 계정, 댓글ID·부모댓글ID·상태. 전체 댓글과 분리 |
| AI 요청·결과 | requestId·원본버전·모드·조건·잠금·선택 범위·DAY 결과·미배치·경고·구간 출처·mock 구분 |
| 번역 | 원문ID/버전·언어·용어집버전·번역문·자동/검수/재번역 상태 |

행 번호나 DAY 표시 문자열만을 영구 참조키로 쓰지 않음. 기존 데이터 이전은 복원 가능하게 적용하고 실패 시 원본을 보존함. 동일 숙소의 DAY 1 방문과 DAY 2 방문을 하나로 합치지 않음.

## 8. 검수와 실행 환경

현재 웹 명령은 루트 `package.json` 기준임. 새 환경에서는 스크립트와 Node 버전을 먼저 확인함.

```text
npm run web:typecheck
npm run web:build
node --test web/tests/typography.test.cjs
node --test web/tests/visits.test.mjs web/tests/localRepository.test.mjs web/tests/tripPlacement.test.mjs web/tests/journeyCreation.test.mjs web/tests/aiTravelDraft.test.mjs web/tests/aiTravelSelection.test.mjs web/tests/photoCaption.test.mjs
```

기존 TypeScript 직접 읽기 테스트는 확인된 Node 24 계열 환경에서 실행함. 개발 서버는 기존 실행 프로세스를 먼저 확인하고 필요할 때 `npm run web`으로 시작함. 포트가 다르면 실제 응답이 오는 주소를 확인한 뒤 사용자에게 전달함. 127.0.0.1 링크만 알려주고 열리는지 확인하지 않은 상태를 완료로 처리하지 않음.

필수 화면 검사: 320·390·460px / 일반·선택·빈 목록·오류·긴 스크롤·팝업 / Android 키보드·하드웨어 뒤로가기·앱 재실행. 브라우저 폭 검사를 실제 Android 확인으로 대체하지 않음.

단위검사는 데이터 관계·실패·취소를, 화면 검사는 레이아웃·조작·복원을 확인함. 이번 실행 문서 제작에서는 제품 단위검사·빌드를 새로 수행해 전체 완료를 확인한 것이 아님.

## 9. 완료·중단 기록 형식

구현을 처음 시작할 때 `docs/execution/PROGRESS.md`를 생성하고 이후 **기존 기록을 보존하면서** 추가함. 최신 요약은 `docs/handoff/CURRENT_HANDOFF.md` 맨 위에도 링크함. 날짜를 이유로 일괄 완료하거나 미검증 항목을 체크하지 않음.

```markdown
## YYYY-MM-DD · P1-XX 작업명

- 상태: 진행 / 검수 / 완료 / 보류
- 요청 범위와 기준 HEAD:
- 실제 변경 파일:
- 기존 로컬 수정 보존 확인:
- 구현한 동작:
- 단위검사·타입 검사·빌드 명령과 결과:
- 화면/기기 검수: 폭, 상태, 실제 기기 여부, 캡처 위치
- 데이터 보존 및 출처 확인:
- 미검증/실패/차단 결함과 재현 절차:
- 일정 변경: 사유, 추가 작업일, 다음 예정일
- 다음 시작 작업 ID와 바로 할 일:
- 서버 연결 여부: 샘플 / 실제 (실제인 경우 별도 승인 근거)
- 커밋·푸시·배포: 없음 (별도 승인 시 대상과 결과 기록)
```

중단할 때 미완료 코드가 있으면 파일·재현·마지막 정상 상태를 기록함. 문제를 숨기려고 사용자 변경을 되돌리지 않음. 이전 차수에 데이터 손실·잘못된 여행/DAY·타인 데이터 노출·조작 차단이 남으면 다음 차수 완료를 선언하지 않음. 증거 없는 성공 주장 대신 확인된 것과 남은 것을 나눠 전달함.

## 10. 이후 백엔드와 별도 운영 범위

| 후속 단계 | 범위 |
|---|---|
| B1 | 회원·권한·동기화·로컬 여행 이전·이미지 저장소·계정 삭제·백업 |
| B2 | 공급자 계약·자동 수집/갱신·중복 통합·업로드 최적화·실제 공개 URL·검색/페이지네이션 |
| B3 | 실제 조회·담김·좋아요·댓글/답글·신고/차단·관리자 처리 |
| B4 | 권리 있는 내부 RAG·실제 인기·주변 후보 매칭·교통·일정 엔진·LLM 안내·번역·품질/예산 |
| B5 | 푸시·오프라인·현장 기록·앱 링크·추가 언어·공동 편집 |

콘텐츠 운영 목표인 서울·부산·제주 각 스팟 20곳 내외와 사진 2~3장 확보, 작성자 모집·홍보·실사용 성과 집계는 별도 운영 작업임. 1차의 3일 샘플 점검을 이 전체 수급이 완료되는 일정으로 해석하지 않음. 9개 일정 시나리오에서 자료를 못 구한 경우 미확보·대체 가능한 검증 범위를 기록하고 권리 없는 이미지를 사용하지 않음.

API 요금·계약·지원 모델은 변할 수 있으므로 실제 연결 시 공식 자료를 재확인함. 과거 문서의 단가·모델명을 현재 확정 조건으로 실행하지 않음. 숙박 예약·결제·가격 비교·음성 실시간 통역은 이번 프런트엔드 차수 범위가 아님.

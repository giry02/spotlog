## 1. 이번 일정의 적용 범위

기존 프론트엔드 시연 일정에 백엔드를 덧붙이는 대신, 남은 작업을 20개로 나누고 실제 담당자의 시간을 배정했다. AI 도구는 개발 보조이며 별도 전담 인력으로 계산하지 않는다. 고객은 제품 판단과 검토를 맡고, 데이터/RAG·앱·QA 전담 인력이 추가로 있다고 가정하지 않는다.

총 예상 작업량은 **107~136인일**, 프론트 담당 **49~63인일**, 백엔드 담당 **58~73인일**이다. 두 사람이 동시에 일하는 기간과 두 사람의 작업일 합계는 다르므로 총 인일을 달력 날짜로 그대로 읽지 않는다.

이 문서는 최신 협업 인원을 반영한 일정 제안이다. 앞선 [화요일 보고 일정](TUESDAY_CLIENT_REVIEW_SCHEDULE.md)의 2026-12-22 최종 검수 목표를 협업·출시 일정의 기준으로 사용하지 않는다. 기존 PHASE_1/2/3의 기능 정의·검수 항목과 제품 보존 원칙은 참고하되, 최초 날짜나 샘플 전용 범위를 이번 실제 연동 일정과 혼동하지 않는다.

### 산정 전제

- 프론트·백엔드 각 1명이 프로젝트에 주 5일 배정된다. 다른 프로젝트 병행으로 가용 시간이 줄면 재산정한다.
- 기존 React/Vite 화면과 Expo WebView 앱 구조를 재사용한다. 전면 디자인 교체·네이티브 재작성은 포함하지 않는다.
- 실제 로그인 방식 1종, 사용자별 여행·사진 저장, 기본 소통·관리, 실제 AI·RAG·교통·영어, 모바일웹과 Android/iOS 출시 준비를 포함한다.
- AI는 외부 모델 API와 관리형 저장/검색 기반을 우선하는 구성으로 산정한다. 자체 GPU 모델 운영·모델 학습을 전제로 하지 않는다.
- 데이터 검수량은 첫 공개 지역 최대 3곳, 초기 장소·업체 합계 약 100~200건을 가정한다. 첫 2주에 실제 수량·자료 상태·확보 경로를 확인한다. 전국 대량 매칭이나 별도 콘텐츠 제작 사업의 공수가 아니다.
- 고객 또는 자료 보유 측이 순위의 의미·원천·대표 업체 목록·서비스 계정 정보를 제공한다. 기존 순위 서버/API의 실제 존재와 재사용 가능성은 아직 확인되지 않았으므로, 첫 2주에 샘플로 확인한다.
- 고객 피드백은 원칙적으로 3영업일 안에 한 번에 취합하는 운영안을 제안한다. 무응답을 승인으로 간주하지 않는다.
- 대규모 추천 알고리즘 연구, 전국 콘텐츠 완비, 숙박 예약/결제, 음성 통역, 상시 위치 추적, 공동 편집, 완전한 오프라인, 고도화된 푸시는 별도 산정한다.

### 인력 용량 확인

주 5일 모두를 새 기능 구현으로 채우지 않는다. 각 담당자의 가용 평일 중 70%를 위 계획 작업에 배정하고, 나머지 30%는 정기 협의·고객 대응·코드 검토·일상 연동 문제에 남긴다. 휴일을 빼면 일반 주의 계획 작업 용량은 담당자별 약 3.5인일이다.

2026-09-16~2027-03-02의 평일은 120일이며, 이번 표에 반영한 평일 공휴일 9일을 제외하면 111일이다. 담당자별 계획 작업 용량은 111 × 0.7 = **77.7인일**이다. 프론트 상한 63인일, 백엔드 상한 73인일은 이 범위 안에 있으나, 백엔드의 잔여 여유가 더 작다.

따라서 전체 24주는 단순히 기능을 24주 동안 계속 추가하는 일정이 아니다. 1월까지 기능 연결을 목표로 하고 2월에는 통합·베타·기기·심사를 다룬다. 추가 예비 2주는 새로운 기능을 담는 용량으로 사용하지 않는다. 스토어 심사나 공급자 처리 지연이 예비 기간을 넘으면 실제 영향을 보고하고 다시 산정한다.

첫 2주에 실제 업체 표본·순위 자료·API 시험·현재 코드 재사용 범위를 확인한 뒤 이 추정치를 보정한다. 숫자는 아직 측정된 개발 속도나 확정 견적이 아니다.

## 5. 업체 ID·순위·좌표와 RAG를 연결하는 작업

사용자가 설명한 주안반점 사례를 다음과 같이 구현한다. 네이버 원문을 RAG에 모으는 작업으로 대체하지 않는다.

| 구성 | 책임 |
|---|---|
| 내부 장소/업체 기준정보 | 실제 매장·지점을 구분하는 내부 ID, 이름·주소·좌표·출처·상태·확인일 |
| 내부 순위 | 지역·업종·집계 시점·점수/순위와 내부 업체 ID |
| 외부 식별자 연결 | 공급자가 실제 제공하는 식별자와 내부 ID의 검증된 대응. 제공되지 않는 외부 ID를 가정하지 않음 |
| RAG 자료 | 설명/근거, 내부 업체 ID, 원문 버전·사용 범위·출처·갱신/삭제 상태 |
| 지도·일정 | 내부 업체/장소 ID에서 조회한 좌표와 별도 방문 ID. 같은 장소의 여러 DAY 방문 구분 |

순위 조회 → 내부 업체 ID → 현재 주소/좌표 조회 → 목록/지도 표시 순서로 연결한다. AI가 업체를 선택해도 주소·좌표·최신 순위는 기준정보에서 조회한다. 순위 정렬 자체를 벡터 검색이나 모델의 기억에 맡기지 않는다. 기존 placeId가 실제 지점을 구분하면 이를 재사용하고, 새 companyId를 중복 도입하지 않는다.

D01은 매칭·순위 연결 기능, D06은 실제 자료의 지점/좌표/사진 검수다. 업체명이 같다는 이유만으로 합치지 않고 주소·지점·좌표를 비교한다. 자동 매칭이 불명확한 항목은 검수 대상으로 분리한다. 주소가 좌표로 변환됐다는 사실과 해당 지점이 맞다는 판단을 구분한다.

09/29까지 대표 업체 50~100건에서 ID 존재율·주소/좌표 누락·동명/중복·지점 구분·순위 연결 가능성을 조사한다. 실제 공개에 사용할 자료는 확인한 항목만 사용한다. 자료 규모·상태가 산정 전제와 다르면 D01/D06과 후속 AI 날짜를 보정한다.

- 서버 기본 로그·키 관리·권한 검사는 B01부터 적용하고, 백업/이전은 B02에서 준비한다. O01은 뒤늦은 최초 보안 설정이 아니라 전체 복원 훈련·운영 한도·문서·배포 복원 검수다.
- 가입·개인정보·계정 삭제·문의·신고 경로, 스토어 설명/스크린샷, 심사 계정, 운영 담당과 비용 한도를 출시 전에 준비한다.
- 빌드 생성, 시험 배포, 스토어 제출, 승인, 실제 공개를 별도 상태로 기록한다. 03/02 공개는 필요한 승인과 검수 통과를 조건으로 한다.

Google Play의 적용 대상 신규 개인 계정은 최소 12명의 테스터가 14일 연속 참여하는 비공개 테스트 후 프로덕션 접근을 신청해야 한다. 2월에 계정을 처음 확인하지 않도록 앞 단계에서 준비한다. [Google Play 테스트 요건](https://support.google.com/googleplay/android-developer/answer/14151465?hl=ko)

Apple은 빌드를 업로드한 뒤에도 앱 버전과 제출 정보를 준비해 심사 제출 절차를 완료해야 한다. 시험 배포나 업로드 성공을 정식 공개 완료로 보고하지 않는다. [Apple 앱 심사 제출](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/submit-an-app/)

## 10. 단계 완료와 오픈 판단

| 확인 영역 | 최소 확인 기준 |
|---|---|
| 사용자 기록 | 저장·복사·이동·삭제/복구·이전·재실행이 원본과 다른 여행을 손상하지 않음 |
| 업체/지도 | 공개 대상의 ID·지점·주소·좌표를 검수하고, 순위와 핀이 같은 업체를 가리킴 |
| 자료/RAG | 자료의 업체 ID·출처·버전·공개 권한이 연결되며 삭제·비공개를 반영함 |
| 실제 AI | 선택/필수/제외·예약·변경 범위를 지키고, 근거 없는 장소/좌표를 적용하지 않음 |
| 경로 | 지원 지역·수단·구간을 명시하고 추정/미지원/조회 실패를 확인된 이동과 구분함 |
| 소통/권한 | 실제 두 계정에서 카드별 반응이 분리되고 본인 권한으로만 수정함 |
| 영어/앱 | 한글 원문·주소·숫자와 입력 상태 유지, 양 OS의 주요 조작·재실행 확인 |
| 운영 | 백업에서 복원 시연, 오류/비용 관측, 한도·문의/신고·배포 복구 담당과 절차 확인 |
| 출시 | 중대 데이터 손실·권한 노출·핵심 조작 차단이 남지 않고 고객 수용 검수 및 스토어 조건 충족 |

응답 시간·동시 사용량·허용 오류율·요청당 비용은 실제 공급자·예산과 사용 목표를 확인해 09/29까지 검수 기준 초안을 정하고, 첫 AI/부하 측정 후 구체화한다. 지금 근거 없는 처리량이나 정확도 수치를 완료 기준으로 확정하지 않는다.

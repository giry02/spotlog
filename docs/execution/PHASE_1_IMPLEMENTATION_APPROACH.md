## 3. 사용자 흐름별 구현

### 발견·저장·내 여행

1. 지역 안내나 사진 피드에서 장소를 확인하고 저장함.
2. 저장에서는 작은 가로 카드·지역 필터·기존 상단 카드 형태를 유지함.
3. 개별 ‘담기’는 기존 팝업에서 사진, 대상 여행, 실제 존재하는 DAY를 확인함. 새 여행이면 제목·기간·선택 출발일·DAY를 받음.
4. 승인 순간 최신 소유 여행과 DAY를 다시 검사하고 저장함. 저장 성공 뒤에만 해당 여행의 해당 DAY 상세를 엶.
5. 북마크 해제는 방문 기록을 유지함. 팝업의 특정 방문 해제는 선택한 여행·DAY·visitId만 대상으로 함. 저장 본문에 방문 편집기를 새로 만들지 않음.

저장 화면의 별도 ‘새 여행’ 진입이 부족한 경우 기존 카드/팝업 안에 짧은 행동으로 연결함. 선택 장소 목록을 전달해 기존 여행 생성 함수를 재사용하고, 생성 후 이름·기간·순서·내용 편집은 내 여행으로 모음.

### 저장 AI와 홈 AI

두 진입은 같은 미리보기·승인 구조를 사용하되 **입력 장소의 범위는 유지함**.

- 홈 AI: 기존 글 입력과 지역·기간·속도·이동수단 확인을 유지함.
- 저장 AI: 저장 장소와 선택 기간을 초기값으로 받음. 글을 다시 입력하도록 강요하지 않음. ‘저장한 곳만’으로 초안을 구성하고 다른 내부 장소를 자동 보충하지 않음.
- 사진 카드를 확인하고 방문별 제외·재포함을 수행한 뒤 승인함. 전부 제외하면 생성을 막되 빈 DAY와 사용자가 정한 기간을 유지함.
- 기존 `AiTravelSheet`에 입력 출처/초기 조건을 전달하는 최소 확장을 검토함. 두 생성 함수를 무조건 하나의 추천 알고리즘으로 합치지 않음.
- 1차에서는 로컬 초안과 세션 단위 요청 무효화·중복 승인 방어만 연결함. 실제 RAG·LLM, 복잡한 조건 해석, 부분 재생성 계약은 3차/백엔드 범위임.

저장 AI의 기존 기간 버튼을 유지하는 경우 팝업의 초기값으로만 사용함. 장소 수를 이유로 사용자가 선택한 기간을 몰래 축소하지 않으며, 여행 기간과 개별 담을 DAY는 계속 독립된 값임.

## 4. 사진 갤러리의 구체적 구현

### 사진 데이터와 출처

제품 DB 전체를 바꾸지 않고 공통 사진 조회 경계를 마련함. 신규 필드명은 구현 시 기존 타입과 대조하여 정하되 다음 의미를 보장함.

| 필드 | 역할 |
|---|---|
| mediaId | 사진의 안정된 ID. 표시 순서나 빌드 결과 URL과 분리함 |
| placeId | 연결된 내부 장소. 이름 유사성만으로 사진을 가져오지 않음 |
| image·alt·caption | 서비스 이미지, 대체 텍스트, 사진 설명. 출처 문구와 분리함 |
| sourceId | 기관·저작자·원문·이용 조건·확인일을 보존하는 자료 레코드 참조 |
| 검수/자료 구분 | 공공자료 검수 기록, 시연 이미지, 미확인 자료를 구분함. 사실·권리를 추정해서 채우지 않음 |

- `Place`에 선택적 사진 목록을 추가하거나 내부 사진 사전을 연결하고 공통 조회 함수로 읽음. 이번 방안의 기본은 **명시한 사진 목록 → 확인된 장소별 사전 → 기존 단일 대표 사진**의 호환 순서임.
- 명시적인 빈 목록·권리 철회 상태는 옛 대표 사진으로 되돌리지 않음. 확인된 철회와 단순 네트워크 실패는 다른 상태임.
- 기존 공공자료의 `source.id`와 `placeId`를 우선 재사용함. 새 자산에만 새 mediaId를 부여함. 기존 이미지 URL 출처 조회는 옛 저장/복사본을 읽는 호환용으로 유지함.
- 사진 URL이 바뀌어도 안정된 ID와 출처가 유지되어야 함. 같은 원본이라도 다른 지점이면 별도 장소로 유지하고, 별칭 연결은 검증된 매핑만 허용함.
- 새 선택 필드는 백업·복원 검증에도 반영함. 필드가 없는 구버전 자료를 거절하거나 사용자 사진/캡션을 일괄 변환하지 않음.
- `motionImages`는 별도 사진 모션 실험 값으로 유지함. 갤러리 자료로 무조건 가져오지 않음.

### 기존 카드 안에서만 탐색

- `LandmarkGuideCard`의 이미지 영역만 확장함. 기존 사진 높이 205px·카드 R21·본문 여백과 제목/소개 역할은 유지함.
- 사진 영역에 가로 scroll-snap 기반 탐색, 이전/다음, 현재 순번을 제공함. 기존 브라우저 스크롤·버튼 방식을 활용하고 갤러리 의존성 추가는 기본안에 넣지 않음.
- 0장은 준비 중, 읽기 실패는 실패 안내로 구분함. 1장은 넘김/순번을 숨기고 2장 이상은 양 끝에서 멈춤. 자동재생·무한 반복은 없음.
- 선택 상태는 숫자 index만 저장하지 않고 현재 mediaId를 기준으로 추적함. 목록 정렬 변경에도 같은 사진을 유지하고 삭제된 경우 유효한 사진으로 보정함.
- 이미지·alt·설명·출처는 하나의 현재 사진에서 함께 파생함. 이전 사진의 저작자·출처가 남지 않도록 함.
- 이미지 요청은 보이는 카드의 현재/인접 사진을 우선하고 나머지는 지연함. 실패 사진에서 다른 유효 사진으로 계속 이동할 수 있게 함.
- 사진 조작의 키보드 이벤트는 해당 갤러리에 초점이 있을 때만 처리함. 세로 스크롤, DAY 선택, 저장/공유/담기, 팝업 닫기를 실행하지 않음.

### 세 화면 연결과 상태 보존

지역 안내, AI DAY 미리보기, 담기 팝업이 이미 `LandmarkGuideCard`를 사용하므로 같은 데이터 조회·렌더링을 공유함. 각 화면의 저장/공유·방문 포함/제외·담김 해제 버튼은 기존 `actions` 슬롯을 유지함.

사진 선택 상태는 화면의 카드 인스턴스별로 보존함. AI는 안정된 방문 키를 사용하여 같은 장소의 DAY 1/2 카드를 구분하고, 사진을 넘겨도 방문 포함 상태를 건드리지 않음. 목록 복귀가 필요한 화면은 화면 식별자+장소/방문 ID의 임시 UI 상태로 기억하며 사용자 여행 데이터에는 저장하지 않음.

출처는 기존 `PhotoCredit`와 `BottomSheet`의 상세 보기를 확장하여 사용함. AI/담기에서는 같은 패널 안에서 출처를 확인한 뒤 사진·입력·선택 DAY·스크롤 위치로 복귀함. 저장 썸네일·본문 임베드·전체 화면 피드는 각 역할의 레이아웃을 유지하고 사진 데이터와 출처 연결만 공유함.

원본 최초 일정은 2026-09-15~2026-10-30임. 30일은 남은 모든 기능을 다시 만드는 기간이 아니라 기존 기능 검수와 결함 수정까지 포함한 예상 작업량임. 최초 기준 검수 후 실제 잔여량을 조정하며 6일 예비를 신규 요구로 자동 소비하지 않음.

콘텐츠 부족은 초반 기준 조사에서 먼저 목록화하고 P1-12에서 검수 결과를 마무리함. 같은 장소의 서로 다른 실제 사진·출처가 확보되지 않은 경우, 소유한 격리 fixture로 UI 분기를 검증한 결과와 실제 자산 연결 미완료를 구분함. 서울·부산·제주 각 20곳의 대량 수급을 3일 콘텐츠 작업에 포함하지 않음.

## 6. 완료 검수와 개발 시작 조건

| 검수 | 필수 사례 / 판정 |
|---|---|
| 여행·DAY | 소유 여행 2개+타인 원본, 1/2/7일, 날짜 미정/실제 날짜, DAY 2 승인→DAY 2 상세, 같은 DAY 중복과 다른 DAY 재방문 |
| 데이터 보호 | 구버전·손상·용량 초과·접근 거부·잘못된 복원 파일·복원 취소. 실패 전후 원본과 방문/본문 참조 비교 |
| 목록 복귀 | 0/1/여러 페이지, 지역·검색 연속 변경, 상세/탭 왕복. 조건·표시 개수 복원 후 스크롤을 복원함 |
| 갤러리 | 0/1/여러 사진, 양 끝, 일부 실패·느린 로딩·권리 철회·긴 출처. 사진 전환과 여행/방문 선택을 독립 검사 |
| 팝업 | 스크롤 아래에서 가로 넘김·출처 확인·DAY 선택·Esc/뒤로가기/닫기. 입력·현재 사진·초점·위치 복원 |
| AI 승인 | 미리보기/취소 시 여행 생성 0건, 전체 제외/재포함, 연속 승인 시 1건, 취소/입력 변경 뒤 늦은 응답 무시 |
| 콘텐츠 | 4개 공공 샘플·11개 사진의 기존 기록 대조. 서울/부산/제주×기간 3종의 검증 시나리오와 실제 확보량 분리 |
| 화면·기기 | 320/390/460px의 일반/선택/빈/오류/스크롤 상태. Android 키보드·하드웨어 뒤로가기·앱 재실행은 별도 확인 |

실제 착수 때 `docs/execution/PROGRESS.md`를 생성하여 작업 ID별 요청 범위·기준 HEAD·변경 파일·검증·미검증·다음 작업을 누적함. 관련 요약만 CURRENT_HANDOFF 맨 위에 연결함. 캡처는 격리 데이터로 `artifacts/phase-1-qa/`에 보관함.

처음에는 기존 사용자 브라우저와 분리된 테스트 origin/프로필을 사용함. 사용자 localStorage에 fixture를 넣거나 기존 앱 데이터를 초기화하지 않음. 실제 Android가 공개 URL을 보는 셸이면 그 결과로 미공개 로컬 기능을 검증했다고 기록하지 않음. 연결된 로컬 코드 버전과 기기 실행 환경을 먼저 확인하며 새 APK 빌드·배포를 자동 시작하지 않음.

코드 변경 후 관련 상태 단위검사, `npm run web:typecheck`, `npm run web:build`, 타이포그래피 회귀를 수행함. 갤러리 데이터/선택/사진 제거와 기존 승인 경로의 실패를 확인하는 검사를 추가함. 단순 구현을 그대로 따라 쓰는 테스트 대신 사용자 기록·상태 불변 조건을 검사함.

**1차 완료:** 잘못된 여행/DAY 변경, 데이터 손실, 승인 전 생성, 사진별 출처 불일치, 팝업 조작 차단이 없고 필수 화면·기기 증거가 있는 상태임. 환경이 없는 기기 검수와 부족한 실제 콘텐츠는 미검증/미확보로 기록하며 전체 완료를 선언하지 않음.

## 7. 2차·3차로 넘길 경계

- 2차: 자동 임시 저장·편집 복구, 안정된 DAY/방문/본문 카드 관계, DAY 이동·독립 복사, 스팟 주변 업체·숙박 거점, 여행기ID+카드ID별 좋아요·댓글/답글, 상세 지도 연결을 확장함.
- 1차에서는 기존 visitId를 보존하고 신규 갤러리 UI 상태를 방문/본문 ID로 대체하지 않음. 현재 `JourneyDay`는 숫자 day 중심임을 인계하고 안정된 dayId·cardId 전체 이전은 P2-01과 맞춤.
- 3차: 상세 조건, 내부 후보/근거 샘플, 추가 업체 승인, 부분 재생성·고정 일정·원문 버전, 관광 안내·영어/번역 상태를 확장함.
- 실제 로그인·서버 저장·집계·TourAPI/네이버 자동 수급·RAG·LLM·교통·번역 공급자는 후속 B1~B5에서 연결함. 1차 모델·요금·외부 API 계약을 지금 확정하지 않음.
- MapLibre worker 404는 과거 공개본의 알려진 기록임. 새 재현 없이 현재 결함으로 단정하지 않고 P2-13으로 인계함. 1차 핵심 조작까지 막는 결함이 재현되면 차단 이슈로 별도 기록함.

## 8. 이번 확인 결과와 한계

- 네 실행 문서와 최신 인수인계·로컬 추가 기록·1차 상태, 관련 개발/AI 계획, 디자인 가이드 §3 및 카드/팝업 규격, 데이터 수급 계획을 대조함.
- 활성 App·담기·홈 AI·방문·저장소·사진 피드·큰 카드·공공자료 출처 코드를 읽음. 철회 시안을 활성 코드로 사용하지 않음.
- 기존 8개 테스트 파일 **60개 통과, 실패 0개**. 실행 환경은 현재 Node `v26.2.0`임. 인수인계에 기록된 Node 24 검증과 이번 실행 환경은 구분함. 실제 구현 착수 시 팀의 검증 런타임을 맞춤.
- 실행 명령: `node --test web/tests/typography.test.cjs web/tests/visits.test.mjs web/tests/localRepository.test.mjs web/tests/tripPlacement.test.mjs web/tests/journeyCreation.test.mjs web/tests/aiTravelDraft.test.mjs web/tests/aiTravelSelection.test.mjs web/tests/photoCaption.test.mjs`.
- 테스트는 메모리 fixture·파일 읽기 기준이며 사용자 브라우저 기록을 사용하지 않음. 구 보관함 관련 테스트 통과는 철회 UI를 복원할 근거가 아님.
- 이번에는 제품 타입 검사·빌드·브라우저 화면·Android·외부 데이터 권리 재조사를 실행하지 않음. 과거 검증 이력은 최신 실행 결과와 구분함.
- 설치된 Expo `~57.0.15`와 [SDK 57 버전 문서](https://docs.expo.dev/versions/v57.0.0/)를 확인함. 1차 화면 변경은 기존 React/Vite 웹에서 수행하고 Expo 하이브리드 셸을 유지하는 방안임.
- 이번 산출물은 이 구현 방안 문서 1개임. 실제 시작 작업은 **P1-01의 격리 기준 화면·현재 동작 기록**이며, 기존 테스트 60개 통과만으로 P1-01이나 1차 전체를 완료 처리하지 않음.

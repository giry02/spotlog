# AI 여행 생성 방향 정정 — 완성된 일정부터

2026-09-20 · 최초 설계 검토 후 사용자 지시로 로컬 구현 완료. 아래 ‘현재 구현의 문제’는 수정 전 진단 기록이다. 현재 구현·검증·제한은 [수정 보고](AI_COMPLETE_ITINERARY_RESULTS_20260920.md)를 따른다. 실제 AI/네이버 연결 전이며 Git 반영은 하지 않았다.

## 사용자 지시로 확정한 방향

- 사용자가 원하는 여행을 문장으로 요청하면 일정을 먼저 만들어 준다.
- 음식점과 숙박을 포함할지 제외할지는 요청 내용에 따라 달라져야 한다.
- 식당은 단순히 가까운 업체가 아니라 점심/저녁 등 식사 목적과 앞뒤 방문이 정해진 일정 항목이어야 한다.
- 업체 후보 선택·검색·직접 등록은 생성 중 거쳐야 하는 단계가 아니라 생성 후 수정 행동에 둔다.
- 기존 디자인을 유지하고 처음 만들 때의 입력·판단 부담을 줄인다.

## 현재 구현의 문제

`generatePlannerSample`은 랜드마크를 선정하고 DAY에 나눠 넣는다. 식사·숙박 요청은 실제 업체 자동 배치로 이어지지 않으며, 생성된 방문에 식사 구분이나 방문 시간대가 없다. `readQuickPlannerPrompt`의 자동 반영도 지역·기간·일부 속도/교통 표현 위주다. 결과의 업체 후보/직접 등록을 기본 노출하므로 사용자가 일정을 조립해야 한다.

저장 장소 모드는 다른 지역의 장소도 모두 유지하고 지역 혼합을 경고문으로만 처리한다. 사용자 첨부의 협재해수욕장·안목해변·서울숲을 같은 DAY로 나눈 결과는 지역 간 이동을 고려한 여행으로 볼 수 없다. 이를 단순한 버튼/글자 수정이나 안내문 추가로 해결하지 않는다.

이전 재검수의 200개 통과는 구현한 선택/저장/복구 규칙의 검증이다. 위 생성 경험과 동선의 실용성을 확인한 결과로 해석하지 않는다.

## 구체적인 흐름 제안

요청 입력 → 필요한 경우 핵심 모호성 한 가지 확인 → 생성된 일정 → 내 여행에 저장 또는 일정 수정.

첫 결과에는 DAY별 오전·점심·오후·저녁·숙박 흐름과 실제 배치한 장소가 보인다. 예시는 ‘오전 협재 방문 → 협재 주변 점심 → 오후 오설록 방문 → 예약한 숙소’와 같은 구조다. 정확한 시각을 산정할 자료가 없다면 시간대를 먼저 제안하고 검증된 방문 시각처럼 표시하지 않는다. 실제 식당/숙소 이름은 이용 가능한 등록 자료에서만 사용한다.

요청 해석의 예:

| 요청 | 생성 행동 |
|---|---|
| ‘제주 1박 2일, 맛집도 넣어줘’ | 관광과 점심/저녁을 함께 배치하며 식사 전후 방문 연결 |
| ‘카페는 빼줘’ | 카페를 자동 추가하지 않음 |
| ‘숙소까지 추천해줘’ | 숙박일과 다음 날 출발을 고려한 숙소 포함 |
| ‘호텔은 이미 예약했어’ | 새 숙소 추천 제외. 이름/위치가 있으면 고정 기준으로 사용; 없으면 임의 호텔을 채우지 않음 |
| ‘관광지만 짜줘. 식사는 알아서 할게’ | 업체 선택을 요구하지 않고 관광 동선 중심으로 생성 |
| ‘저장한 곳으로 만들어줘’ | 같은 권역을 우선 묶고, 시간/이동상 함께 쓸 수 없는 권역을 한 DAY에 나열하지 않음 |

언급이 전혀 없는 일반 요청의 기본값은 구체화가 필요한 제안이다. ‘전체 여행을 짜줘’는 기본 식사 흐름과 여러 날의 숙박 제안을 포함하고, ‘산책 코스/방문할 곳만 추천’은 장소 중심으로 해석하는 방향이 적합하다. 숙박 예약 여부 등 결과를 크게 바꾸는 조건만 짧게 확인하고 긴 체크리스트를 선행하지 않는다.

결과에서 ‘점심 바꾸기’는 그 점심 위치와 DAY를 유지한 후보를 연다. ‘장소 추가’는 사용자가 선택한 방문 사이에 끼워 넣고 영향을 받는 이후 일정만 조정한다. 숙소 변경도 여행 전체를 다시 고르게 하지 않는다. 기존 후보·검색·개인 등록·초안 보관은 이 수정 흐름에서 재사용할 수 있다.

## 다음 구현의 검수 조건

1. 같은 요청의 포함/제외/예약 표현이 최종 결과에 실제 반영되는가.
2. 추가 선택 없이 그대로 사용할 수 있는 초안이 먼저 나오는가.
3. 모든 식사의 목적과 앞뒤 장소, 숙박일과 다음 날 출발이 구분되는가.
4. 지역 간 이동이 필요한 장소를 같은 반나절/하루에 무리하게 배치하지 않는가.
5. 후보 부족/영업·이동 미검증을 숨기거나 가짜 업체·시각으로 채우지 않는가.
6. 수정 화면의 추가/교체가 현재 DAY·방문 위치를 유지하는가.
7. 저장/닫기/새로고침 복구와 기존 6개월 휴지통 규칙을 보존하는가.

이 문서는 제품 방향 정정과 수정 방안이며, 자동 식사/숙박/시간대 생성이 이미 구현된 것으로 표시하지 않는다. 실제 AI·경로 서비스 연결을 완료했다는 의미도 아니다. GitHub 반영·배포 없음.

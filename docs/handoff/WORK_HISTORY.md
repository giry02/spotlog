# Spotlog 작업 이력·사용자 결정사항

정리일: 2026-09-09. 현재 대화의 사용자 요청과 저장소에서 확인한 결과를 주제별로 기록함. 모든 항목이 운영 서비스로 구현되었다는 뜻이 아니며, 과거 답변 원문을 재현한 문서도 아님. 최신 상태는 CURRENT_HANDOFF.md가 우선함.

## 1. HotelNGo에서 Spotlog로 분리

### 최신 정정 · 2026-09-10

사용자가 프런트엔드는 혼자 구현하며 1차·2차·3차를 기능 개발 단위로 사용할 것이라고 명시함. 이전 3주 일정과 개발자 A/B/C 역할 배정은 폐기함. 개발 요약본에는 합본 1쪽과 각 차수 상세 1쪽씩을 포함하도록 개정함. 이하 과거 주차·인원 언급은 당시 이력이며 현재 지침으로 사용하지 않음. 최신 원본·요약·CURRENT_HANDOFF를 우선함.

- README와 MIGRATION_FROM_HOTELNGO.md를 기준으로 codex/mobile-foundation에서 모바일 작업을 진행하도록 요청함.
- 사용자는 100% 네이티브가 아니라 모바일웹과 앱을 혼용하고, 앱 기능이 필요한 부분만 네이티브로 쓰길 원함.
- 실제 구성은 Expo WebView 셸 + React/Vite 웹으로 정리됨. HotelNGo의 예약/결제·회원·데이터를 그대로 공유하는 통합 서비스로 설명하지 않음.
- 모바일웹은 설치 없이 바로 열람하는 방향임. 앱 설치를 강요하는 진입이 아님.

## 2. 여행기 서비스의 핵심 요구

- 한 사람은 하나가 아니라 여러 여행을 만들 수 있어야 함.
- 실제 여행을 일기장/블로그처럼 작성하고, 다른 사람이 글과 사진을 상세히 읽으며 장소와 동선을 볼 수 있어야 함.
- 단순 방문 순서만이 아니라 무엇을 보고, 숙소가 왜 좋고, 주변에서 어떤 경험을 할 수 있는지 글 속에 장소 항목이 나타나야 함.
- 다른 사람 여행기를 읽고 복사하여 내 것으로 수정하는 기능과 직접 만드는 기능을 모두 유지함.
- 호텔·숙소·음식점·카페는 직접 입력할 수 있어야 함. 초기부터 모든 업체를 데이터화할 수 있다는 전제를 버림.
- 숙박 실제 비용·객실 재고·예약은 하지 않음. 업체 기본 정보와 경험의 공유를 우선함.
- 국내 여행으로 시작함. 제주 서쪽 2박 3일을 글/사진/장소/지도까지 갖춘 샘플로 만드는 요청이 있었음.

## 3. 콘텐츠와 디자인 피드백

- 초기 아이콘/디자인이 유치하고 폰트 크기가 불규칙하다는 피드백이 반복됨. 작게 줄이기보다 모바일 가독성과 일관성을 우선함.
- 이미지를 쇼츠처럼 단순히 대체하는 것은 초기 영상 의도와 다르다고 지적함. 이후 수급 문제를 고려해 풀영상과 사진 모션을 병행하는 별도 방향을 제안함.
- 같은 사진의 위아래 반복, 차밭에 마사지 사진, 해변에 호텔 사진 등 실제 장소와 불일치한 예시는 품질 문제임. 시각적 차이만 만들려고 다른 장소 사진을 넣으면 안 됨.
- 장소 카드 사이에 주변 사진·느낌·좋은 점·평가·현장 팁을 충분히 넣어 가이드처럼 읽히길 원함.
- 쓸데없이 만든 초기 여행기를 정리하고 완성도 있는 한 편만 남겨 달라는 요청 후, 후속 단계에서 기간별/지역별 샘플을 늘려 달라고 요청함. 최초 한 편만 유지하라는 요구를 영구적인 샘플 수 제한으로 적용하지 않음.

## 4. 지도·이동·뒤로가기

- HotelNGo trip-planner처럼 지도 마킹 후 도로 이동 경로와 방향 화살표, 소요 시간을 보여 달라고 요청함.
- 현재 MapLibre + OpenStreetMap 표시, OSRM 도로 경로, 구간 시간/거리·번호 핀·이동 표시 구현이 있음. 길찾기 실패 시 추정 정보는 실제 경로와 구분해야 함.
- 카카오 지도 전환, 개발 키/허용 도메인 설정, 회사 명의 전환 관련 질문이 있었음. 키 값 자체는 인수인계 MD에 복사하지 않음.
- 이후 사용자가 카카오 지도를 원복하고 나중에 처리한다고 명시함. 지금은 카카오 내장 지도 재전환을 진행하지 않음.
- Kakao Local을 업체명/주소/좌표 후보 검색에 사용하는 방향은 검토 대상임. 사진 확보까지 제공된다고 가정하지 않음.
- 뒤로가기 404, 스크롤 하단에서 탈출 불가, DAY 버튼이 헤더에 가려지는 문제를 지적함. 공개 여행기와 내 여행 모두 동일하게 접근 가능해야 함.
- 최종 UX는 DAY 1 앞의 뒤로가기 화살표임. 별도 고정 헤더는 상단 공간과 디자인 때문에 원하지 않음.

## 5. 홈·여행기·장소 탐색

- 쇼츠가 메인인 화면에서 다른 사람의 일정과 추천/홍보 일정을 읽는 별도 홈으로 변경 요청함.
- 목적지가 있으면 지역 검색, 없으면 추천 여행을 선택한 뒤 읽고 복사·수정하는 구조임.
- 여러 추천/여행자 일정이 롤링되도록 요청하여 캐러셀 구현이 추가됨.
- 추천 카드에서 곧바로 수정이 아니라 일정보기를 먼저 제공해야 함.
- 다른 여행자 여행기 검색 카드는 홈 아래로 내리고, 위아래 여백과 다른 섹션의 좌우 여백을 맞추도록 수정함.
- 프로필은 홈에서 진입하고 하단에서는 제외함. 하단은 홈/여행기/장소/내 여행/저장으로 구성됨.
- 영상 메뉴는 장소 탐색의 한 형식으로 취급함. 지역 가이드형 장소 목록과 영상 모두 같은 장소를 담는 구조임.
- 여행기 검색에 지역과 기간, 당일치기 구분을 넣는 요구가 있었음.

## 6. 저장함·지역·여행 DAY

- 지역별로 담고 전체/지역별로 다시 볼 수 있어야 함. 큰 KPI 카드 대신 서울 몇 개, 경기 몇 개처럼 간결한 지역 표시를 원함.
- 지역이 많아도 모두 볼 수 있도록 가로 스와이프 등 탐색을 보장해야 함.
- 펼쳐보기 버튼 대신 스크롤 자동 로딩을 요청함. 현재 장소 가이드는 최초 3개, 하단 가까이에서 3개씩 추가하는 기준임.
- 저장한 장소로 여행을 만드는 상단 기능과 샘플을 요청하여 로컬 자동 일정 생성이 추가됨.
- 이미 담긴 장소는 누른 후 토스트만으로 알려 주지 말고 DAY 배지와 해제 상태를 카드에서 표시해야 함.
- 여행 기간 2일 선택과 실제 담을 DAY 2 선택의 혼동 및 DAY 1로 들어가는 버그가 있었음. DAY 선택 시 해당 날짜가 없다는 오류가 난 뒤, 필요한 DAY 생성 방식으로 보완됨.
- 현재 대상 여행과 기간/DAY를 분명히 분리하는 것은 이후 프런트엔드 1주차의 중요 보완 과제임. 기존 버그 수정으로 전체 상태 설계가 완성되었다고 단정하지 않음.
- 자동 생성 제목에 'AI가 엮은' 같은 불필요한 표현을 빼 달라는 요청이 반영됨.

## 7. 작성 동기·커뮤니티·알림

- 내 여행을 다른 사람이 담아간 횟수, 긍정적 반응과 댓글, 작성자 등급을 보여 동기를 주길 원함.
- 여행기 하단 댓글, 작성자 프로필/다른 여행 목록, 아바타·등급, 사용자 사진 업로드를 요구함.
- 조회수 등이 일정 기준에 도달하면 앱 푸시를 보내고, 수신 켜기/끄기를 제공하길 원함.
- 현재 관련 화면과 로컬 저장/샘플 동작이 존재하지만 실제 사용자 간 집계·원격 푸시가 구현된 것은 아님. 샘플 수치를 실제 성과로 설명하지 않음.
- 후속 서버 개발에는 중복/자기 반응 방지, 원본/복사본 관계, 신고·차단·관리자 처리와 안전한 발행이 포함됨.

## 8. GitHub 공개·Android

- 저장소 giry02/spotlog에 올리고 실제 열람 주소를 달라는 요청에 GitHub Pages 배포 구성이 추가됨.
- 사용자는 '푸시하지 말라고 하기 전엔 언제나 푸시'라는 작업 선호를 명시함. 요청 범위에 있는 변경만 테스트 후 커밋/푸시함.
- APK 제작을 요청했고 중단/나중 확인/적당히 안 되면 멈추라는 후속 요청도 있었음. 사용자 최신 요청 없이 무한 빌드 재시도를 하지 않음.
- Expo/EAS preview APK와 production AAB 구성이 있음. 앱에서 공개 GitHub Pages URL을 로딩하는 구조임.
- 사용자가 웹을 부르는 껍질인지, 약 85MB인 이유를 질문했음. 네이티브 셸과 의존성 때문에 웹 파일 크기와 같지 않지만, 이번 인수인계에서 APK 내부 용량 분석이나 새 빌드는 하지 않았음.

## 9. 확장 방향·외국인·개발 계획

- 향후 추가 기능을 보고하고 MD로 저장하라는 요청으로 FUTURE_ROADMAP.md가 생성됨.
- 기존 구현과 겹치는 제안을 줄이고 실제 부족한 부분을 재조사하라고 요청함.
- 외국인이 로컬 가이드처럼 읽고 여행할 수 있어야 하며, 국내 콘텐츠를 먼저 쌓고 다국어로 넘어가는 단계가 중요하다고 명시함.
- 단순 번역 외에 교통 이용법, 한글 주소, 현장 안내, 문화/결제/예약 필요 정보가 있어야 함. 지도 제공자의 한국 내 정보 품질과 외국어 지원을 함께 검토함.
- 유사 서비스의 장점을 조사하여 확장 방향에 포함하고, 전체 개발을 3차로 나누라고 요청함.
- 최종 일정은 개발자 2~3명, 총 3주 프런트엔드 우선, 백엔드는 이후임. 주마다 설계 1일/구현 3일/통합 검수 1일 기준으로 계획함.
- 계획서에 있더라도 이번 복구 작업에서 기능 개발을 착수하지 않음.

## 10. 발표형 HTML 보고서의 형식

- 확장 내용을 HTML 보고서로 만들되 '~함' 형태의 보고용 문체를 원함. '메모체'는 카드형 메모 UI를 뜻하지 않음.
- 사용자는 한 장씩 넘기는 프레젠테이션을 원했으며, 일반 HTML을 발표형으로 바꾸면서 내용을 줄인 것에 강하게 이의를 제기함.
- 원래 항목·상세 글·표·출처를 보존하고 필요한 경우 페이지를 늘려야 함. 글씨를 극단적으로 줄이거나 큰 빈 페이지로 만들지 않음.
- 흰색 본문·네이비 표지·포인트 색과 서체 위계를 따르고 이전/다음/방향키/목차/페이지 번호/인쇄를 제공함.
- 현재 확장 보고서는 보존하고, 별도 일반 개발 계획서 32쪽과 AI 계획서 57쪽이 공개되어 있음.
- 57쪽 AI판은 이전 34쪽 주제를 유지하면서 내부 RAG·모델·비용 등 23쪽을 추가한 결과임.

## 11. AI 논의가 바뀐 지점

### 처음 계획

선택한 장소를 기간·숙소·교통·체류 시간에 맞게 배치하고, OR-Tools와 경로 공급자를 이용하여 시간 제약을 검사한 뒤 LLM이 설명하는 방식이었음. 관광 안내와 자동번역은 별도 기능으로 분리함.

### 사용자의 핵심 보완

'OR-Tools가 무엇이며 원하는 기능과 같은가', 'GPT에 어디 가고 무엇을 먹는지 물어보는 것과 어떤 차이인가', 'GPT 외 모델도 있는데 어떤 방식이 맞는가'를 이해할 수 있게 설명하라고 요청함.

이후 **내부 로우 데이터를 RAG화하여 해당 지역의 인기 랜드마크와 고객 메타 조건에 맞는 장소를 추리고, 가까운 내부 인기 음식점·숙박을 자동 매칭**하는 것이 핵심 의도임을 명시함.

### 현재 정리

- 후보 추천과 시간표 최적화는 별개의 계층이며 둘 중 하나로 대체하지 않음.
- RAG는 내부 근거 검색, DB는 좌표/조건/권한/인기 수치, LLM은 조건 이해와 설명/후보 조합 보조를 담당함.
- 음식점은 인기뿐 아니라 식사 시간·거리·다음 동선·조건을, 숙소는 여행 전체 거점과 여러 날의 이동 부담을 고려함.
- 일정 엔진은 실제 경로로 검증하고, OR-Tools는 복잡한 시간 제약이 필요할 때 사용하는 선택 도구임.
- 데이터 부족은 명시하고, 외부 검색 보완을 내부 인기 추천인 것처럼 표시하지 않음.
- 선택 장소만 구성/지역·취향 추천/외부 보완의 세 가지 모드를 분리함.
- 모델 이름을 최종 승자로 단정하지 않고 같은 후보와 과제로 품질·가격·응답 시간 평가 후 선택함.
- 가격표의 공식 확인일·프로모션·조건·토큰 가정을 명시하고 실제 서비스 전체 월 비용과 혼동하지 않음.

## 14. 이번 복구 준비의 이유

사용자는 대화 이력이 길어지면 창이 깨질까 걱정하며 현재 세션 용량을 질문함. 로컬 세션 메타데이터에서 입력 약 21만/문맥 한도 25.84만 토큰을 확인함. 별도로 누적 로그 약 322MiB가 있었음. 이 기록은 시점별 수치이며 이후 자동 요약으로 달라질 수 있음.

사용자는 새 대화를 만들어 인수인계하고 지금까지 작업을 MD로 저장하라고 명시함. 이에 현재 상태/이력/전체 계획서를 남기며, 새 작업에는 읽고 준비한 뒤 대기하라는 요청만 전달함. 대화 원문 로그·비밀키·브라우저 개인정보를 공개 저장소에 올리지 않음.

## 2026-09-10 · 랜드마크 사진 넘겨보기를 1차에 포함

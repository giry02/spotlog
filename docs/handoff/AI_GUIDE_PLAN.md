## 02 / 67 · AI 개발 범위와 기본 결정

01 · EXECUTIVE SUMMARY

내부 데이터 기반 추천을 중심에 두고, 모델의 후보 조합·설명과 실제 이동·일정 검증을 분리함.

### 첫 추천·일정 기능에 포함

- 지역·취향 추천과 저장 장소 구성 모드를 구분함

- 자동차·대중교통·도보를 모두 구분함

- 1~7일·선택 장소 최대 30곳을 검증 범위로 삼음

- 랜드마크·식당·숙소 매칭, 고정 일정·미배치·부분 수정·관광 안내를 제공함

### 후속 단계로 분리

- 음성 가이드와 실시간 통역을 분리함

- 백그라운드 위치 추적과 자체 내비게이션을 제외함

- 예약·결제·호텔 실제 숙박비를 다루지 않음

- 일본어·중국어와 자체 모델 학습은 후속 검토함

**프런트엔드 단계에서는 화면과 샘플 응답을 구현함.** 실제 AI·번역·경로 호출은 서버 기반과 공급자 사용 조건을 갖춘 뒤 연결함. 수동 여행 작성에는 AI의 7일·30곳 제한을 적용하지 않음.

## 05 / 67 · 여행 전·여행 중·언어 지원

01 · USER EXPERIENCE

새 하단 메뉴를 늘리지 않고 기존 저장·여행 상세 흐름 안에서 기능을 제공함.

| 상황 | 진입 위치 | 제공 내용 |
| --- | --- | --- |
| 여행 전 | 홈·저장의 만들기·AI 하단 입력 | 하단 팝업에서 장소·조건·후보를 확인함. 승인 후 비공개 내 여행 상세로 이동함 |
| 여행 수정 | 내 여행의 일정 조정 | 특정 DAY·오후·남은 일정만 변경, 고정 장소 유지, 적용 전 비교 |
| 여행 중 | 오늘 DAY 또는 선택한 장소의 관광 안내 | 다음 장소 이동, 볼거리·이용 팁, 질문, 출처·확인일·미확인 안내 |
| 영어 이용 | 언어 설정과 여행기 원문·번역 전환 | 영어 설명, 한글 이름·주소 크게 보기, 번역 상태와 피드백 |

홈은 자연어 여행 요청, 저장은 저장 장소 기반 만들기를 제공함. 하단 입력·초안 확인 후 비공개 내 여행 상세를 엶. 편집·관광 안내는 내 여행에서 이어가며 자동 발행하지 않음.

## 06 / 67 · 추천의 중심은 Spotlog에 쌓인 데이터임

RAG · PRODUCT DECISION

2026.09.09 보완 방향. “선택한 장소를 정렬하는 엔진”에서 “우리 데이터로 갈 곳을 고르는 추천”까지 범위를 명확히 함.

### 사용자가 기대하는 결과

- 지역·동행자·관심사에 맞는 인기 랜드마크를 추림

- 그 주변의 적합한 음식점·숙박을 우리 데이터에서 매칭함

- 여행기 속 추천 이유와 실제 작성자의 근거를 함께 보여줌

- 사용자가 대화로 바꾸고 내 여행에 저장할 수 있게 함

### 기술의 우선순위

- 핵심: 내부 데이터 정리 + 조건 검색 + RAG + 추천 순위

- LLM: 요청 이해, 후보 조합, 근거 있는 안내문 작성

- 경로: 실제로 이동 가능한지와 이동 부담을 검증함

- OR-Tools: 복잡한 시간·순서 제약이 있을 때 추가함

**RAG와 OR-Tools는 경쟁하는 선택지가 아님.** RAG는 무엇을 추천할지에 근거를 공급하고, OR-Tools는 정해진 후보를 어떻게 배치할지 계산하는 선택 도구임.

출처: [RAG 원 논문](https://arxiv.org/abs/2005.11401) · [OR-Tools 시간 창 배치](https://developers.google.com/optimization/routing/vrptw)

## 07 / 67 · 여행을 만드는 세 가지 방식을 구분함

RAG · MODES

추천할 권한과 여행에 최종 저장할 권한을 분리함. 자동 매칭은 초안 생성이며 자동 발행·예약이 아님.

| 방식 | 장소를 고르는 기준 | 추가·승인 규칙 |
| --- | --- | --- |
| ① 지역·취향 추천 | “부산 2박 3일, 부모님과 바다·음식 중심”처럼 조건만 입력함 | 허용된 내부 장소에서 랜드마크·식당·숙소를 자동 매칭한 초안을 보여줌. 검토 후 여행으로 저장함 |
| ② 저장 장소로 구성 | 사용자가 고른 장소를 우선하거나 해당 목록만 사용함 | “선택한 곳만”이 기본임. 식당·숙소 자동 보완을 켠 경우에만 내부 후보를 초안에 추가함 |
| ③ 외부 자료로 보완 | 우리 데이터가 적을 때 별도로 제안함 | 사용자가 범위 확대에 동의한 경우에만 외부 후보를 검색함. 내부 인기·여행기 추천과 구별함 |

여행 기간 “2일”은 일정의 길이이며 “DAY 2에 담기”는 목적 날짜임. 어떤 추천 방식에서도 이 두 상태를 연결하지 않음.

## 08 / 67 · 기술 용어를 역할로 이해함

RAG · TERMS

“데이터를 RAG화한다”는 것은 글을 검색 가능한 상태로 준비하고, 찾은 근거를 답변 생성에 연결한다는 의미임.

| 용어 | 쉽게 설명하면 | Spotlog에서 하는 일 |
| --- | --- | --- |
| LLM | 질문을 이해하고 글을 구성하는 언어 모델 | 여행 조건 해석·후보 조합·가이드 설명 |
| 임베딩 | 글의 의미를 비교하기 위한 숫자 표현 | “한적한 산책”과 비슷한 내용의 여행기 찾기 |
| RAG | 자료를 찾아서 읽힌 뒤 답변하게 하는 방식 | 관련 여행기·장소 설명을 LLM의 근거로 제공 |
| 추천 순위 계산 | 후보 중 적합한 것을 앞에 놓는 규칙 | 취향·인기·신뢰도·이동 부담 함께 비교 |
| 경로 API | 도로·교통망에서 이동을 조회하는 서비스 | 도보·차량·대중교통의 시간과 경로 확인 |
| OR-Tools | 제약을 지키는 배치를 찾는 계산 도구 | 시간 고정·장소가 많은 일정의 순서와 DAY 배치 |

검색용 임베딩 생성은 자체 LLM 학습이나 미세조정과 다름. 초기에는 모델을 새로 학습하지 않고 내부 검색과 기존 모델을 연결함.

## 09 / 67 · 조건부터 추천·일정까지의 전체 흐름

RAG · END-TO-END FLOW

LLM에 원본 데이터 전체를 한 번에 보내지 않음. 서버가 조건에 맞는 후보와 근거를 골라 필요한 범위만 전달함.

STEP 1 **조건 해석** 지역·취향·필수 조건 확인

STEP 2 **후보 검색** 권한·지역 필터와 의미 검색

STEP 3 **순위·매칭** 인기와 취향, 식당·숙소 조합

STEP 4 **추천 초안** 허용 후보로 구성·이유 설명

STEP 5 **이동 검증** 교통·시간 충돌과 배치 조정

STEP 6 **사용자 확인** 변경 이유 확인 후 저장

### LLM에 제공하는 자료

- 후보 장소 ID·확인된 정보·원문 근거 ID

- 계산된 인기 지표와 표본 수·확인 시점

- 사용자 조건과 제외·고정 항목

### 서버가 다시 검사하는 항목

- 후보 밖 장소·가짜 인기 수치·없는 근거 차단

- 이동 검증 실패 시 후보 교체 또는 경고 반환

- 최종 수정에 맞춰 설명도 갱신하고 승인받음

순서는 단방향 고정이 아님. 숙소·식당 또는 이동 부담에 따라 랜드마크 조합도 다시 검토하되, 사용자 고정 장소는 임의로 바꾸지 않음.

## 10 / 67 · 원본 데이터를 어떤 단위로 쌓을 것인가

RAG · RAW DATA

여행기 통째로만 저장하면 업체별 인기와 주변 매칭을 계산하기 어려움. 글·장소·방문·반응을 고유 ID로 연결함.

| 데이터 단위 | 필수 연결 정보 | 활용 |
| --- | --- | --- |
| 장소 | placeId, 종류, 지역, 좌표, 이름·주소, 출처·확인일 | 같은 업체의 표기 차이를 통합하고 위치·종류로 검색함 |
| 여행기·본문 블록 | storyId, blockId, 작성자, placeId, 원문·버전·공개 범위 | 특정 장소에 대한 후기와 추천 이유를 출처로 제시함 |
| 여행 내 방문 항목 | visitId, DAY, placeId, 체류·이동, 계획/방문 기록 구분 | 같은 숙소의 여러 DAY 이용과 장소 간 연결을 표현함 |
| 행동 이벤트 | 저장·복사·해제·반응, 사용자, 시간, 원본 계보 | 중복·취소를 반영한 실제 관심 지표를 계산함 |
| 사진·설명·메타 | assetId, placeId, 이용 권리, 원문 설명, 조건 태그 | 장소와 맞는 콘텐츠 및 취향 근거를 확보함 |
| 근거·검색 색인 | sourceId, blockId, 원문 버전, 접근 권한, 색인 버전 | 수정·삭제·비공개 전환을 검색과 답변에 반영함 |

기존 샘플 조회수·댓글·등급은 인기 계산에서 제외함. 계획에 담았다는 사실을 실제 방문·숙박한 경험으로 바꾸어 해석하지 않음.

## 11 / 67 · 고객 조건은 필수와 선호로 나눔

RAG · CUSTOMER METADATA

지역·취향 같은 메타는 검색 필터와 순위 계산에 사용함. 모든 입력을 단순 태그 일치나 LLM의 추측으로 처리하지 않음.

| 조건 | 처리 | 미확인 정보 처리 |
| --- | --- | --- |
| 지역·기간·출발·고정 방문 | 검색 범위와 일정의 반드시 지킬 조건으로 사용함 | 지명 중복이나 날짜 미입력은 확인하거나 개략 계획으로 표시함 |
| 이동수단·걷기 한도 | 이용 가능한 경로와 일정 제약으로 검사함 | 좌표상 가까워도 실제 보행 가능 여부는 따로 확인함 |
| 바다·사진·한적함·미식 | 본문 의미와 작성자 태그를 함께 찾아 순위에 반영함 | 모델이 추출한 태그는 추론 태그로 구분함 |
| 동행·접근성·식사 조건 | 사용자가 제공한 조건만 사용하고 중요한 항목을 별도 확인함 | 후기의 “가족에게 좋음”을 휠체어·알레르기 안전 보장으로 바꾸지 않음 |
| 인기·숨은 장소·다양성 | 사용자 선호에 따라 내부 인기와 새로운 후보의 비중을 조정함 | 인기 근거가 없으면 검수 추천 또는 데이터 부족으로 표시함 |

한적함 선호는 조용하다고 평가된 장소를 찾는 조건임. 실시간 혼잡도가 없으면 “지금 사람이 없다”고 답하지 않음.

## 12 / 67 · 여행기가 검색 자료가 되는 과정

RAG · INDEXING

검색 색인은 원문을 대신하는 별도 데이터베이스가 아니라 다시 만들 수 있는 검색용 사본으로 관리함.

- **장소 연결·권한 확인** 공개·이용 허용된 여행기만 추천용으로 수집함. 사용자 자신의 비공개 여행은 해당 사용자 요청에서만 별도 권한으로 조회함.

- **장소별 의미 단위로 나눔** 한 장소의 설명·평가·팁을 묶고 장소가 바뀌면 분리함. chunk에 원문 위치·작성자·장소·버전을 남김. 긴 글은 문맥이 끊기지 않게 분할함.

- **검색 표현을 준비함** 한글명·별칭·키워드 색인과 본문 임베딩을 생성함. 좌표·공개 범위·인기 숫자는 구조화 데이터로 별도 보관함.

- **변경 사항을 동기화함** 원문 변경분만 재색인함. 삭제·비공개 전환은 검색·캐시·생성 결과 접근에 반영하고, 답변 직전에도 현재 권한과 버전을 재검사함.

추천 근거에는 원문 링크와 필요한 짧은 인용·요약만 제공함. 다른 작성자의 글 전체를 새로운 여행기인 것처럼 재작성하지 않음.

## 13 / 67 · 의미 검색만으로 인기 장소를 찾지 않음

RAG · HYBRID RETRIEVAL

RAG는 검색과 생성의 결합임. 숫자 집계·거리·조건은 DB가 담당하고, 여행기 표현의 유사성은 의미 검색으로 보완함.

| 순서 | 처리 방식 | 이유 |
| --- | --- | --- |
| 1. 범위 제한 | 권한·지역·장소 종류·필수 조건으로 후보를 제한함 | 다른 지역이나 접근 불가 자료가 섞이는 것을 차단함 |
| 2. 두 방식 검색 | 장소명·별칭 키워드와 본문 의미 검색 결과를 합침 | 정확한 지명과 “비 오는 날 쉬기 좋은 곳”을 모두 찾기 위함 |
| 3. 후보 정리 | 동일 placeId를 합치고 여러 원문의 근거를 묶음 | 글이 많은 한 업체가 검색 결과를 독점하지 않게 함 |
| 4. 추천 순위 | 취향 적합도·내부 인기·근거 품질·이동 부담을 계산함 | 의미 유사도와 인기도는 서로 다른 점수임 |
| 5. LLM 전달 | 상위 후보의 ID·정보·근거·계산 점수만 전달함 | 없는 장소를 만들지 않고 선택과 설명에 집중하게 함 |

시험 시작값 예: 검색 80개 → 중복 통합 30개 → 모델 전달 15개. 고정 정답이 아니며 검색 누락률·응답 비용을 측정해 조정함.

## 14 / 67 · “우리 서비스에서 인기”의 기준을 정함

RAG · POPULARITY

인기도는 LLM이 후기 몇 개를 읽고 추정하는 값이 아님. 실제 행동을 집계한 서버 지표이며 산식 버전을 기록함.

### 인기 지표 준비

- 최근 일정 기간의 고유 사용자 저장·복사·반응을 집계함

- 저장 해제·자기 반응·자동화·중복 복사를 보정함

- 같은 지역·장소 종류 안에서 비교하여 규모 차이를 줄임

- 표본이 적으면 과대평가를 보정하고 낮은 신뢰도를 표시함

- 노출 수가 쌓이면 클릭·저장 전환과 노출 편향도 함께 점검함

### 최종 추천 순위

- 필수 조건을 먼저 통과한 후보끼리 순위를 비교함

- 취향 적합도 + 내부 인기 + 근거 품질을 고려함

- 되돌아감·긴 이동·비슷한 장소 중복에는 감점을 적용함

- 신규 장소에는 별도 탐색 기회를 두되 인기인 척하지 않음

- 홍보 일정·협찬은 별도 표시하고 인기 점수에 숨기지 않음

“인기”를 고르면 적합한 후보 중 인기 지표가 높은 곳을 우선함. 가중치는 초기 가설이며 실제 선택·저장·완료 평가로 조정함. 특정 비율을 검증된 정답으로 고정하지 않음.

## 15 / 67 · 랜드마크 주변 음식점을 자동 매칭함

RAG · RESTAURANT MATCHING

랜드마크 바로 옆의 최다 조회 업체가 항상 좋은 선택은 아님. 사용자의 조건과 그날 동선에 맞는 내부 후보를 찾음.

- **내부 후보를 확보함** 랜드마크와 다음 방문 권역 주변에서 음식점 placeId를 찾음. 공간 반경은 후보 검색용으로만 사용하고 실제 이동 시간은 경로로 확인함.

- **취향·시간·근거를 확인함** 음식 종류·식사 시간·확인된 영업 정보와 동행 조건을 비교함. 중요한 식이 정보가 없으면 확인 필요로 남김.

- **인기와 함께 등장한 관계를 반영함** 같은 여행기에 함께 포함된 음식점 관계와 고유 사용자 저장·복사 지표를 참고함. 복사 계보·동일 작성자 반복·표본 수를 보정함.

- **조합을 비교해 초안에 넣음** 되돌아감이 적고 조건에 맞는 후보를 제안함. 추천 이유·원문 출처·대체 후보를 보여주고, 자동 보완을 끈 경우에는 별도 후보로만 남김.

“이 장소를 방문한 사람이 먹은 곳”은 실제 방문 기록이 확인된 경우에만 사용함. 단순 동시 등장 데이터는 “같은 여행기에 함께 담긴 곳”으로 표현함.

## 16 / 67 · 숙소는 여행 전체의 거점으로 매칭함

RAG · LODGING MATCHING

랜드마크마다 가까운 호텔을 하나씩 붙이지 않음. 숙박일과 전체 동선을 기준으로 숙소·숙박 지역 후보를 비교함.

| 판단 항목 | 매칭 방식 |
| --- | --- |
| 이미 정한 숙소 | 사용자의 숙소를 고정하고 랜드마크·식당 동선을 그 기준으로 구성함 |
| 숙소 미정 | 권역별 후보를 찾고 여러 DAY의 출발·복귀와 첫날 도착·마지막 출발 부담을 함께 비교함 |
| 이동 방식 | 차량이면 주차·진출입, 대중교통이면 역·정류장과 마지막 도보 정보를 확인함 |
| 우리 데이터의 평가 | 내부 저장·복사와 숙박을 기록한 원문의 장점·주의점을 근거로 제시함 |
| 여러 권역 여행 | 숙소 이동의 장단점을 설명함. 이동 부담이 크면 랜드마크 권역과 숙소 조합을 함께 재검토함 |
| 상품 정보의 한계 | 가격 비교·빈 객실·실시간 예약 가능 여부는 포함하지 않음. 인기 숙소라고 예약 가능하다고 표시하지 않음 |

내부 숙소 데이터가 부족하면 숙박 지역까지만 제안함. 외부 숙소 후보는 사용자가 별도 보완에 동의한 경우에만 구분해 제공함.

## 17 / 67 · 내부 데이터 추천 예시 · 후보를 고르는 이유

RAG · WORKED EXAMPLE

부산 1박 2일·부모님 동행·대중교통·바다와 음식·짧은 걷기 조건을 가정함. 아래 장소·점수는 모두 설명용 가상 데이터임.

| 후보 | 내부 근거와 조건 | 처리 |
| --- | --- | --- |
| L1 해안 전망 장소 | 바다 태그·내부 저장 근거 있음 / 긴 계단 구간 확인 | 인기여도 걷기 조건에 맞지 않아 제외함 |
| L2 해변 산책 장소 | 바다·완만한 산책 근거 / 정류장 연결 확인 | 랜드마크 후보로 우선 제안함 |
| R1 인기 음식점 | 지역 내 인기 지표 높음 / 다음 장소와 반대 방향 | 우회 부담 때문에 기본 조합에서 제외함 |
| R2 음식점 | 조건에 맞는 음식 / L2와 같은 여행기 등장 / 다음 동선 부근 | 식사 후보로 매칭하고 원문 근거를 연결함 |
| H1 숙박 장소 | 여러 DAY 이동 거점 / 내부 숙박 후기 근거 | 숙소 후보로 제안함. 요금·예약 가능성은 알 수 없음 |

안내 예: “걷기 조건을 고려해 L2를 골랐으며, R2는 다음 이동 방향에 있고 같은 여행기에 함께 소개된 근거가 있어 제안함.” 순위·거리·작성자 경험을 모델이 새로 만들어내지 않음.

## 18 / 67 · 우리 데이터가 부족할 때의 처리

RAG · COLD START

RAG를 붙인다고 없는 콘텐츠와 인기 지표가 생기지는 않음. 지역별 데이터의 충분함과 최신성을 운영 과제로 함께 관리함.

### 초기 확보와 보완

- 서울·부산·제주에서 장소 연결이 정확한 여행기를 먼저 확보함

- 랜드마크뿐 아니라 실제 일정에 쓰인 식당·숙소도 함께 수집함

- 검수 추천·실제 인기·홍보 콘텐츠를 구분해서 표시함

- 주변 정보가 없으면 지역 확대·조건 완화 여부를 물음

### 하지 않을 처리

- 샘플 반응 수를 실제 인기 순위에 사용하지 않음

- 원문이 없는 업체를 “우리 여행자 추천”으로 소개하지 않음

- 외부 검색 결과를 내부 데이터인 것처럼 합치지 않음

- 비공개 여행을 다른 고객 추천용으로 임의 활용하지 않음

직접 작성한 검수 콘텐츠만 있어도 추천을 시작할 수 있음. 다만 사용자의 실제 반응이 충분해질 때까지 “인기” 대신 “검수 추천”으로 안내함.

## 19 / 67 · 3단계 입력 흐름

02 · INPUT FLOW

홈·저장의 하단 입력에서 장소 범위·여행 기본 조건·추가 조건을 확인함. 1차는 간단한 로컬 초안, 아래 상세 조건은 3차 확장 범위임.

- **사용할 장소 선택** 지역·취향 추천 또는 저장 장소 구성을 선택함. 반드시 갈 곳·제외할 곳과 음식점·숙소 자동 보완 여부를 확인함.

- **여행 기본 조건 입력** 기간과 실제 날짜, 첫날 도착·마지막 날 출발, 숙소 또는 숙박 지역, 주 이동수단과 여행 속도를 받음.

- **추가 조건 확인** 고정 방문 시간, 동행자, 걷기 부담, 관심사, 식사·접근성 조건을 선택 사항으로 받음. 기본값과 미입력을 명확히 표시함.

**지역 추천 모드는 내부 장소·업체를 자동 매칭한 초안을 제공함.** 저장 장소의 “선택한 곳만” 모드는 보완을 켜지 않으면 새 업체를 넣지 않음. 두 모드 모두 최종 저장·변경 적용은 승인 후 진행함.

## 20 / 67 · 기간·시간·이동 조건의 해석

02 · CONSTRAINTS

기본값은 시연 시작값이며 사용자가 수정할 수 있음. 운영 조건이 확인된 것으로 오인하지 않게 함.

| 입력 | 초기 처리 기준 | 미입력·충돌 처리 |
| --- | --- | --- |
| 기간·실제 날짜 | 1~7일, 일정 시간대는 Asia/Seoul로 관리함 | 날짜가 없으면 DAY 중심 개략 계획이며 영업·운행일 검증을 하지 않음 |

## 25 / 67 · OR-Tools는 복잡한 배치의 선택 도구임

03 · SCHEDULING ENGINE

관광지를 추천하는 모델이 아니라 제약을 지키는 배치를 찾는 도구임. 초기 규칙·LLM 후보 조합을 경로 검증하고, 복잡한 경우 추가함.

### 입력과 제약

- 방문 간 이동 시간, 방문 체류시간을 입력함

- 날짜별 출발·종료 시간과 숙소를 기준점으로 둠

- 필수 장소·사용자 고정 시간·확인된 영업시간을 우선함

- 휴식·식사 시간과 사용자가 정한 걷기 부담을 반영함

### 배치 우선순위

- 1순위: 고정·필수 조건과 실행 가능한 시간 창을 지킴

- 2순위: 선택한 장소를 가능한 범위에서 포함함

- 3순위: 긴 이동·되돌아감·하루 과밀을 줄임

- 제한 시간 안의 최선 결과를 사용하고 전역 최적을 보장하지 않음

도입 시 DAY별 시작·끝 지점을 가진 배치로 모델링함. 실제 출발 시각으로 재검사하며, 대중교통 변화 시 최대 2회 재배치를 시험 시작값으로 둠. LLM의 순서도 같은 검사 대상이며 이동 시간을 지어내게 하지 않음.

## 27 / 67 · LLM의 역할과 제한

04 · LANGUAGE MODEL

GPT·Claude·Gemini를 비교하며 특정 공급자를 필수로 고정하지 않음. 허용 후보와 근거로 조건 해석·추천 조합·관광 안내를 담당함.

### 허용하는 역할

- “오후만 바꿔줘” 같은 요청을 수정 조건으로 변환함

- 내부 검색·순위 결과에서 조건에 맞는 후보를 조합하고 이유를 설명함

- 검수 자료와 현재 여행을 근거로 관광 질문에 답함

- 설명에 사용한 출처 ID와 확인 필요 항목을 반환함

### 허용하지 않는 역할

- 장소·좌표·주소·영업시간·노선·가격을 임의 생성하지 않음

- 선택한 곳만 모드에 새 업체를 넣거나 고정 일정을 임의 변경하지 않음

- 실제로 다녀온 것처럼 방문 후기·감정을 꾸며 쓰지 않음

- 외부 문서의 지시로 비공개 정보 조회나 도구 실행을 하지 않음

구조화 응답은 형식 검증을 돕는 수단임. 서버에서 장소 ID 허용 목록, 숫자·시간, 근거 출처, 고정 조건을 다시 검사함. 도구 실행은 허용된 함수만 서버가 수행함.

## 28 / 67 · 하나의 모델에 모든 일을 맡기지 않음

MODEL · ROLE SEPARATION

검색용 모델, 답변 모델, 번역 도구는 독립적으로 선택함. 처음부터 여러 모델을 모든 요청에 동시에 호출하지 않음.

| 역할 | 초기 기준안 | 다른 방식이 필요한 때 |
| --- | --- | --- |
| 의미 검색용 임베딩 | text-embedding-3-small로 검색 기준선을 측정함 | 한국어·영어 교차 검색 품질이나 반출 조건 때문에 다른 모델 비교가 필요할 때 |
| 후보 순위 재검토 | DB 규칙·의미 점수로 먼저 구성함 | 검색 누락이 아닌 순서 품질이 병목일 때 재순위 모델을 별도 시험함 |
| 조건 해석·가이드 생성 | Sol / Sonnet 5 / Gemini 3.8 Flash를 동일 사례로 비교함 | 운영 합격 기준을 통과한 모델 중 비용·지연이 낮은 모델을 선택함 |
| 짧은 분류·정리 | 규칙으로 가능하면 모델 없이 처리함 | 자유 문장 해석이 필요할 때 Luna 등 경량 모델을 시험함 |
| 콘텐츠 번역 | Cloud Translation Advanced + 용어집을 기준안으로 둠 | 중요 문장 오류가 남을 때 선별 검수·다른 번역 엔진 비교를 진행함 |

임베딩 모델과 답변 LLM은 같은 회사일 필요가 없음. 번역·응답 언어도 지도 표시 공급자와 독립적으로 선택함.

## 29 / 67 · GPT·Claude·Gemini를 어떻게 비교할 것인가

## 42 / 67 · 자동번역·검수·원문 변경 처리

07 · TRANSLATION PIPELINE

번역문이 원문보다 오래되거나, 수정된 정보를 계속 보여주는 문제를 방지함.

- **원문과 구조화 필드를 분리함** 본문·사진 설명을 번역 대상으로 추출함. 장소 ID·주소·전화·날짜·숫자·출구 번호와 사용자 입력 참조는 보호함.

- **번역 결과를 버전별로 저장함** 콘텐츠 ID + 원문 버전 + 대상 언어 + 용어집 버전을 기준으로 결과를 재사용함. 동일 요청은 중복 처리하지 않음.

- **자동 검증 후 상태를 표시함** 블록 누락과 숫자·부정 표현·용어 오류를 검사함. “자동번역”과 “검수 완료”를 구분하고 원문 보기·피드백을 제공함.

- **원문 변경 시 재검토함** 원문 수정으로 기존 번역을 재검토 상태로 바꿈. 중요 필드가 바뀌면 오래된 내용을 확정 정보로 표시하지 않고 새 번역을 준비함.

번역 실패 시 한국어 원문과 재시도 방법을 유지함. 화면 열람마다 번역 API를 호출하지 않으며, 삭제한 원문의 번역도 공개 대상에서 제거함.

COST · LIFECYCLE

데이터를 한 번 준비하는 비용과 사용자가 여행을 만들 때 발생하는 비용을 구분함. LLM 단가만으로 월 운영비를 단정하지 않음.

| 비용 단계 | 발생하는 작업 | 계산 기준 |
| --- | --- | --- |
| 초기·변경 색인 | 본문 정리·장소 연결·임베딩·검색 색인 | 최초 원문량 + 변경분 토큰, 검수 인력, 색인 서버 |
| 요청별 검색·추천 | 질문 임베딩·검색·인기 순위·선택적 재순위 | 월 요청 수 × 실제 처리 비용 + 검색 인프라 |
| 추천·질문 생성 | 조건 해석·후보 조합·설명·재시도 | 입력·청구 출력 토큰과 호출 횟수의 합계 |
| 이동·일정 | 교통 경로 조회·검증·선택적 배치 계산 | 실제 공급자 과금 요청 수 + 계산 서버 |
| 번역 | 새 본문·수정 블록·요청한 댓글 번역 | 캐시를 제외한 신규 번역량과 언어 수 |
| 공통 운영 | DB·저장·전송·모니터링·콘텐츠 검수 | 월 기본 비용 + 사용량 비용 + 별도 운영 인력 |

다음 월 계산표에서 “일정 1건 비용”에는 검색용 질문 임베딩·선택적 재순위·모든 LLM 호출을 합산함. 초기 색인·월 변경 색인·운영 인력은 별도 예산으로 관리해 중복 계산하지 않음.

## 51 / 67 · 중복 호출·비용·장애 관리

09 · COST & RELIABILITY

색인·검색·재순위·LLM·경로·번역·계산 서버 비용을 관리함. 초기 색인과 검수 인력은 별도 예산으로 확보함.

### 호출을 줄이는 방식

- 요청 ID로 같은 생성·결제성 과금 요청의 중복 실행을 막음

- 장소·시간·모드 기준으로 허용된 경로 결과만 재사용함

- 30곳 전체 쌍은 최대 870방향이므로 무조건 매번 재조회하지 않음

- 지역 분류·후보 축소·변경 구간 재조회로 범위를 줄임

- 번역은 원문·언어·용어집 버전이 같으면 재사용함

### 운영 통제

- 사용자별 생성·질문·번역 횟수와 전체 예산을 제한함

- 단계별 요청 수·성공률·지연·비용을 기록함

- 공급자 장애 시 재시도 상한과 회로 차단을 적용함

- 비용 상한 시 새 생성은 중지하고 기존 여행 열람은 유지함

- 오류 종류에 따라 경로·배치·설명만 부분 재시도함

“무료 쿼터가 있으니 비용 없음”으로 계획하지 않음. 캐시 허용·보존 기간·최소 계약금·SLA·상업적 표시 범위를 공급자별로 확인함.

## 65 / 67 · 네이버 API HUB 서버 연결 준비

2026.09.10 · DATA & LANDMARK GALLERY

키와 공급자 정책을 서버에서 관리하고, 공식 응답 범위와 오류 상태부터 검증함.

| 기술 항목 | 구현 기준 |
| --- | --- |
| 호출·인증 | 서버가 GET /search/v1/local을 호출함. X-NCP-APIGW-API-KEY-ID·X-NCP-APIGW-API-KEY를 사용하며 웹·APK에 키를 넣지 않음. |

| 응답 검증 | 이름·주소·분류·링크·mapx/mapy를 검사함. 문서상 WGS84라도 실제 값의 단위·스케일을 확인함. 안정적인 공급자 장소 ID가 있다고 가정하지 않음. |
| 제공하지 않는 항목 | 반경 검색·사진·평점·영업시간·경로는 별도 확보 대상임. 전화번호 필드는 빈 값이며 조회 결과에 없는 사실을 만들어 넣지 않음. |
| 한도·비용 확인 | HUB 안내의 한시 무료·월 775,000회 공유·키별 50 RPS와 지역 API의 일 25,000회 설명이 함께 존재함. 콘솔·공식 답변으로 적용 한도와 유료 전환을 확정함. |

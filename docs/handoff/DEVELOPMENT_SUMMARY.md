## 01 / 19 · 추가 개발 계획 핵심

SPOTLOG · 공통 방향 · 1

프런트엔드를 1차·2차·3차로 나누어 구현함. 차수별 완료 조건을 기준으로 진행함.

| 구분 | 요약 |
| --- | --- |
| 제품 방향 | 여행기를 읽고 장소를 저장한 뒤, 내 일정으로 활용하고 여행 후 기록을 발행함. 국내 콘텐츠를 먼저 쌓고 영어 이용을 준비함. |
| 현재 활용 | 홈 추천·여행기 검색, 장소 발견·지역별 저장, 여러 여행과 DAY 편집, 글·사진·장소 블록, 여행기 복사·지도 표시를 활용함. |

## 02 / 19 · 1차·2차·3차 프런트엔드 합본

SPOTLOG · 공통 방향 · 2

1차·2차·3차의 구현 범위와 완료 기준을 정리함.

| 차수 | 구현 범위 | 완료 후 가능한 일 |
| --- | --- | --- |
| 1차 · 발견·저장 | 기존 스타일·검색·사진 쇼츠·카드 사진 넘김·담기·홈 AI 초안 | 저장 하단 팝업에서 여행·기간·DAY를 고름. 확정한 내 여행 상세를 엶. |
| 2차 · 일정·작성·소통 | 임시 저장·복구·사진/글·주변 업체·숙소·카드 반응·댓글·지도·복사 | 여행기를 편집하고 본문 속 장소마다 반응·댓글을 남김. |
| 3차 · 추천·안내 | AI 추천·주변 업체 보완·후보 승인·부분 수정·관광 안내·영어 | 추천 초안 수정·관광 안내·영어 열람을 확인함. |

### 차수 진행 기준

- 각 차수 안에서 구조 정리, 기능 구현, 실패 상태 처리, 전체 흐름 검증을 순서대로 진행함.

- 앞 차수의 기록·상태와 기존 화면 역할별 스타일·컴포넌트를 다음 차수에서 재사용함.

1~3차는 프런트엔드 범위임. 실제 로그인·서버 저장·AI/RAG·교통·번역 연동은 이후 백엔드 단계임.

## 03 / 19 · 전체 페이지 구조 · 메뉴와 하위 화면

SPOTLOG · 공통 방향 · 3

현재 하단 메뉴를 유지하고, 각 메뉴 안의 화면을 연결하며 필요한 기능을 차수별로 보완함.

| 진입 메뉴 | 하위 페이지와 연결 | 개발 배치 |
| --- | --- | --- |
| 홈 | 추천 일정·여행자 일정 → 여행기 읽기 지역·기간 검색 → 여행기 목록 | 기존 활용 / 1차 탐색 정돈 |
| 여행기 | 검색·지역·기간 목록 → 여행기 읽기 작성자 프로필·다른 여행기 / 복사 → 내 여행 | 1차 검색 / 2차 읽기·복사·카드 반응 |
| 장소 | 안내 목록 · 영상 · 사진 쇼츠 랜드마크 상세 → 저장 / 내 여행의 DAY 선택 | 1차 쇼츠·카드 사진 넘김·저장 통일 |
| 내 여행 | 여러 여행 목록 → 여행·DAY 선택 / 생성·상세·편집 기간·DAY·순서·글·사진 수정 / 지도·현장 안내·영어 | 1차 선택·생성 / 2차 작성 / 3차 안내 |
| 저장 | 저장 목록 · 지역 필터 · 작은 가로 카드 → 담기 만들기·AI 하단 입력 → 승인 후 내 여행 상세 | 1차 진입·상태 표시 / 3차 AI 보완 |

**공통 진입:** 프로필은 홈에서 열며 아이콘·등급·내 공개 글·반응·알림 설정을 연결함. AI 관광 안내는 여행 안에서 제공하며 하단 메뉴를 늘리지 않음.

기존 화면을 활용하는 목표 구조임. 새 하위 기능은 1·2·3차에서 보완하며 실제 로그인·동기화·집계·푸시는 후속 서버 단계에서 연결함.

## 04 / 19 · 기능 구조 · 1·2·3차 구현 로드맵

SPOTLOG · 공통 방향 · 4

장소·저장·방문·본문을 공통 기반으로 연결하고, 앞 차수의 결과를 다음 차수가 이어서 사용함.

| 차수 · 연결 영역 | 주요 기능 묶음 | 완료 후 이어지는 화면 |
| --- | --- | --- |
| 1차 · 발견·저장 F01–F06 · F20 | 기존 스타일·검색·사진 쇼츠·카드 사진 넘김·홈 AI 초안 하단 기간·DAY 선택 후 내 여행·담김·해제 | 생성 후 내 여행 상세로 이동해 수정함. 선택한 장소·방문 기록을 2차로 전달함. |
| 2차 · 작성·독자 소통 F07–F12 · F19 | 임시 저장·복구, 글·사진·업체 카드·DAY 편집 이동·복사·지도·미리보기, 카드별 좋아요·스레드 | 읽을 만한 여행기를 작성하고 카드별 반응을 시연함. 편집기와 읽기 화면을 3차가 재사용함. |
| 3차 · 추천·현장 안내 F13–F18 | AI 조건·후보 승인·결과·일부 재생성 관광 안내·영어·원문 보기·전체 회귀 검수 | 저장 진입 → 내 여행 생성·상세 → 오늘 안내. 샘플 연결부를 이후 실제 서버로 교체함. |

### 공통 기능의 연결 원칙

- 사진·영상·안내는 같은 장소와 저장 상태를 사용함. 여행 방문·본문 카드·댓글 대상은 별도 ID로 구분함.

- 읽기·편집·지도·추천 결과는 같은 여행과 DAY를 참조함. 글자·버튼·입력·하단 팝업은 공통 스타일을 재사용하며 오류·복원·뒤로가기를 검증함.

이후 서버: B1 회원·데이터 → B2 콘텐츠·발행 → B3 실제 커뮤니티 → B4 AI·번역 → B5 푸시·현장 앱. 프런트엔드 샘플을 실사용 집계나 실제 AI 결과로 표시하지 않음.

## 05 / 19 · 스팟 보완 기능의 1·2·3차 구현

SPOTLOG · 공통 방향 · 5

기존 각 차수의 작업을 유지하고, 사진으로 확인한 스팟을 주변 업체와 연결하는 기능을 단계별로 추가함.

| 차수 | 추가 구현 | 완료 조건 |
| --- | --- | --- |
| 1차 · 사진으로 확인 | 지역 안내·AI·담기의 큰 카드에 좌우 사진 넘김·순번·출처를 추가함. 저장 본문의 작은 가로 카드는 유지함. | 사진과 장소 정보를 보고 생성·담기를 확정함. 대상 여행·DAY와 실제 결과가 일치함. |
| 2차 · 직접 보완 | 내 여행 스팟의 주변 장소 팝업과 숙박 DAY별 숙소 추가를 구현함. 현재 여행·DAY·스팟 문맥을 이어받음. | 샘플 후보를 스팟 다음에 추가함. 같은 숙소의 여러 날 사용·예약 숙소 고정·취소·중복을 처리함. |
| 3차 · AI 보완 승인 | 내부 후보를 사용한 음식점·숙소 보완 선택, 사진 카드·근거·대안·변경 미리보기를 연결함. | 승인한 후보만 적용함. 고정 장소와 수정 대상 밖 기록은 보존하며 거절·부족·경로 실패를 표시함. |
| 백엔드 이후 | 실제 내부 인기·RAG와 교통 검증을 연결함. 네이버는 계약을 확인한 뒤 별도 외부 검색으로 검토함. | 권한·출처·후보 품질·호출 비용을 검증함. 로컬 샘플을 실제 검색·추천 성과로 표시하지 않음. |

**2차의 기존 소통 기능 유지:** 여행기 속 업체·랜드마크 카드마다 좋아요·댓글 수를 표시하고, 별도 하단 팝업에서 댓글·답글을 보고 작성함. 주변 장소 선택 팝업과 역할을 구분함.

장소 ID와 여행 방문 ID를 분리함. 주변 업체는 기준 방문에 연결하고 숙박은 숙박일·DAY에 연결함. 이동·복사·삭제 시 관계와 다른 날 기록을 함께 검사함.

## 06 / 19 · 데이터 수급과 내부 추천 자료

SPOTLOG · 공통 방향 · 6

공식 기초 정보와 허용된 사진·여행기를 내부 자료로 쌓고, 실제 사용자 반응으로 추천 품질을 높임.

| 수급 항목 | 적용 방향 |
| --- | --- |
| 랜드마크·공식 안내 | TourAPI·지자체에서 장소와 이용 정보를 확인함. 필드별 출처·확인일·권리를 보존하고 미확인 정보는 표시함. |
| 여러 사진 | 관광사진 API·허용된 지자체 자료·직접 촬영·제휴·사용자 사진을 확보함. 같은 장소의 실제 사진만 사용하고 자산별 조건을 검사함. |
| 음식점·숙박 | 현재 공공데이터포털 인허가 자료로 기초 업체 정보를 보완함. 구 LOCALDATA는 2026.04.16 폐쇄되었으며 인허가 정보를 인기·평점·사진으로 간주하지 않음. |
| 권리와 RAG | 공공누리 유형과 개별 조건을 검사함. 표시·보관·변형·임베딩·AI 입력 허용을 구분하고 권리 미확인 자료는 제외함. |
| 초기 확보 목표 | 서울·부산·제주 각각 스팟 20곳 내외·사진 2~3장, 기간별 여행기 총 9개를 준비함. 현재 완료 수치가 아니며 기존 검증 자산도 활용함. |
| 실제 운영 | 인기는 내부 실제 저장·복사·반응으로 계산함. 원문 수정·삭제·권리 철회 시 이미지·색인·번역도 갱신함. |

스팟을 기준으로 주변 음식점·숙소를 연결함. 사용권이 확인된 내부 자료로 추천하고, 네이버 검색 결과는 계약상 허용 범위에서 별도로 제공함.

## 07 / 19 · TourAPI 장소·좌표와 공공 사진 활용

SPOTLOG · 공통 방향 · 7

관광정보와 좌표를 먼저 확보하고, 같은 장소의 이용 가능한 사진을 연결함. API 무료 이용과 사진별 사용 조건을 구분함.

| 항목 | 수집·이용 기준 |
| --- | --- |
| 장소·좌표 먼저 | TourAPI에서 장소명·주소·좌표·소개 정보를 확보함. 누락·좌표계·실제 장소를 확인하며 대표 좌표와 출입구를 구분함. |
| 사진 연결 | TourAPI·관광사진 API·지자체 사진을 같은 내부 장소 ID에 연결함. 사진마다 별도 ID와 출처·작가·이용 유형·원문 링크·확인일을 보관함. |
| 무료 이용 범위 | 국문 TourAPI는 무료이며 호출 한도·운영 승인 절차를 확인함. 관광공사 사이트 전체 사진·글의 무제한 이용 허락으로 해석하지 않음. |
| 사진별 이용 조건 | 1유형은 출처 표시 후 상업 이용·변경이 가능해 편집·사진 모션용으로 우선 확보함. 3유형은 출처 표시·변경 금지 조건으로 원형 사용을 별도 관리함. |
| 화면 출처 | 사진 설명과 출처 메타를 분리함. ‘사진 출처’ 버튼에서 기존 하단 팝업으로 상세를 제공하며 캡션에 같은 문구를 반복하지 않음. |

**적용 순서:** 1차에는 권리를 확인한 소량 샘플·표시·실패 상태를 준비함. 자동 수집·갱신은 B1·B2의 서버 단계에서 연결함.

자료별 허용 조건과 제3자 권리를 확인함. API가 무료여도 사진 저장·전송·검수 비용은 별도임. 실제 연동·대량 수집 완료를 뜻하지 않음.

## 14 / 19 · 2차 · 스팟 주변 음식점·숙소 추가

SPOTLOG · 2차 · 14

스팟으로 DAY별 일정의 기본 구성을 정한 뒤, 내 여행에서 음식점·카페와 숙박 거점을 보완함.

| 화면 | 사용자 동작과 연결 |
| --- | --- |
| 장소 발견·저장 | 가고 싶은 스팟을 저장함. 저장 화면은 기존 목록·지역 필터·여행 만들기 진입을 유지하고 업체 추천·일정 편집을 펼치지 않음. |
| 여행 만들기 | 기간과 DAY를 선택하고 사진 카드로 장소를 확인함. 승인하면 해당 내 여행 상세를 열며 이후 수정은 그곳에서 진행함. |
| 내 여행 · 스팟 주변 | 스팟 카드의 ‘＋ 주변 장소’로 하단 팝업을 엶. 추천 / 직접 검색 / 저장한 장소에서 음식점·카페를 고름. |
| 추가 위치 | 현재 여행·DAY·기준 스팟을 팝업에 표시함. 고른 장소는 기준 스팟 다음에 추가하며 여행과 DAY를 다시 묻지 않음. |
| 숙박과 공개 열람 | 숙소는 숙박할 DAY의 거점으로 추가함. 다른 사람의 여행기에는 편집 동작을 숨기고 읽기·저장·복사 흐름을 유지함. |

**화면 역할:** 저장은 모으기·만들기, 내 여행은 DAY별 보완·관리임. 주변 업체의 직접 선택과 선택적 AI 보완은 같은 후보와 장소 카드를 사용함.

스팟을 먼저 고르는 흐름만으로 동선이 보장되지는 않음. 예약한 숙소·고정 시간은 처음부터 반영하고, 음식점은 다음 스팟 방향과 식사 시간을 함께 검토함.

## 15 / 19 · 2차 · 여행기 속 장소 카드별 소통

SPOTLOG · 2차 · 15

작성자는 여행기 본문에 업체·랜드마크를 넣고, 독자는 각 카드에 좋아요·댓글·답글을 남김.

| 구현 영역 | 화면과 동작 |
| --- | --- |
| 작성·제공 | 저장 장소·검색·직접 입력으로 음식점·호텔·랜드마크 카드를 넣음. 사진·경험·설명과 함께 독자에게 제공함. |
| 카드별 반응 | 각 카드 아래 좋아요 버튼·좋아요 수·댓글 수를 표시함. 좋아요는 누르기/취소, 숫자는 해당 카드의 하단 팝업을 엶. |
| 하단 팝업 | 좋아요 수를 누르면 반응한 사용자 목록, 댓글 수를 누르면 아이콘·이름·시각·본문과 입력창을 보여 줌. 여행기 제목·장소명을 함께 표시함. |
| 댓글·답글 | 댓글별 ‘답글 N개’를 같은 팝업에서 펼침. 답글 대상·취소, 본인 글 수정·삭제, 신고를 제공함. 목록은 나눠 불러오고 키보드 위에서 작성함. |
| 연결·보존 | 여행기 ID + 장소 카드 ID로 스레드를 구분함. 같은 업체라도 다른 여행기의 반응은 섞지 않음. 카드 이동은 유지, 복사본은 새 ID·반응 0건으로 시작함. |

**2차 F19:** 카드 삽입·미리보기·반응·댓글·답글과 실패·로그인 필요 상태를 샘플로 구현함. **이후 B3:** 실제 저장·권한·중복 방지·집계·신고·차단을 연결함.

여행기 전체 댓글·업체 공통 리뷰와 분리함. 좋아요는 카드·계정별 1회, 댓글 수는 공개 댓글·답글 합계임. 닫기·뒤로가기 시 본문 위치·포커스·미전송 초안을 보존함. 샘플 수치는 실제 인기와 구분함.

## 18 / 19 · 후속 개발 · 네이버 연동과 내부 RAG의 경계

SPOTLOG · 후속 개발 · 18

네이버 지역 검색은 외부 검색 확인 경로로 검토하며, 내부 추천용 데이터 적재를 기본 허용으로 가정하지 않음.

| 항목 | 계획에 반영한 판단 |
| --- | --- |
| 신규 연결 | 2026.07.31부터 신규 신청은 NAVER API HUB임. 서버 키로 연결하며 기존 개발자센터 키 유예는 2027.06.30까지임. |
| 검색 범위 | 최대 5건·start 1이며 반경·사진·평점·경로는 제공하지 않음. comment 정렬은 블로그·카페 리뷰 수로, 내부 인기 점수와 구분함. |
| 약관 확인 | 개발자센터의 2026.09.07 시행 약관은 AI 입력·학습·평가, 결과 변경·수익화 등에 제한을 둠. HUB는 별도 계약이므로 적용 범위를 서면 확인함. |
| 기본 사용 경계 | 네이버 결과의 영구 DB·RAG·자체 재정렬·다른 사진 결합·내부 병합은 승인 범위 확인 전 차단함. 사용자 선택만으로 허용되지 않음. |
| 비용·연동 시점 | 공식 문서의 월 775,000회·키별 50 RPS와 지역 API 일 25,000회 설명을 콘솔에서 확인함. 한시 무료를 상시 무료로 계획하지 않으며 실제 연동은 서버 이후임. |
| 외부 검색 변경 | 네이버 API HUB를 별도 외부 검색으로 검토함. 영구 저장·RAG·내부 병합·표시 허용을 계약으로 확인한 뒤 서버 연결 범위를 확정함. 사진·인기 데이터는 별도임. |

내부 추천은 허용된 공공·제휴·사용자 자료와 실제 반응을 사용함. 네이버 신규 키 발급·호출·저장 기능을 이번 문서 작업에서 실행하지 않음.

SPOTLOG · 완료 기준 · 19

기존 기능을 다시 만들기보다 저장의 정확성, 기록 보존, 여행 정보의 신뢰도를 먼저 확인함.

# Windows Flowise·RAG 연결

이 문서는 초기 연결과 75문서 확장 당시의 기록이다. 이후 고정 후보 배치를 실제 RAG 선택 일정으로 바꾸고 API 키 없는 로컬 14B 전환을 연결했다. **현재 구조는 [RAG 일정 생성과 로컬 모델 전환](RAG_ITINERARY_ROUTING_20261015.md)을 기준으로 읽는다.**

2026-10-15 로컬 개발 작업. 맥미니 이전과 공개 Sites 배포는 수행하지 않는다. 원래 Spotlog 앱 저장소와 개인 여행 자료는 유지한다.

## 경로와 역할

브라우저는 Moa `/api/chat`만 호출한다. 서버가 승인된 데모 장소 ID를 정해 로컬 RAG에 검색을 요청하고, 원본 코드의 현재 설명과 문서 hash를 비교한다. Flowise에는 현재 조건·기존 대화·검증한 근거만 전달한다. 모델 응답의 action·ID·예약·명시적 수정 범위를 기존 계약으로 검사하고, 검색 자료를 다시 재검증한 뒤 기존 카드에 적용한다. 카드 상세 열기와 직접 조작은 모델을 호출하지 않는다.

현재 검색 원본은 75문서다. 기존 체험 장소 설명 13개에 제주 공식 안내를 직접 요약한 62개를 추가했다. 제주 28곳에 특징·방문 고려사항을 각 2개씩 쓰고, 권역 계획·버스·비 오는 날·바다 안전 6개를 더했다. 공식 출처 37 URL과 확인일 2026-10-15를 문서별로 보관한다. 원문을 통째로 수집하거나 사진·후기·회원 여행기·예약·개인 대화를 색인하지 않는다. `curated-official-summary`와 `authored-demo-data`를 구분하며 전체 검색 모드는 `curated-travel-data`다. Spotlog 회원 DB와 운영 권리 검수 연결은 별도다.

### 제주 확장과 장애 대응

`lib/jeju-knowledge.ts`가 공식 안내 요약의 원본이고, `lib/rag-catalog.ts`와 CLI가 동일한 문서 ID·텍스트·출처를 만든다. 공식 자료의 사실과 작성자의 계획 제안을 본문에서 구분한다. 새 지식 장소는 설명용이며 일정 카드의 허용 ID를 늘리지 않는다. 출처 URL·제목·확인일도 원본과 비교하고 검색 전후의 자료 검증과 철회 차단을 유지한다.

현재 제주 2박 3일 일정은 LLM이 region/configure/build로 해석한 뒤 앱의 기존 제주 장소 12곳과 서버 배치 규칙으로 구성한다. 완성된 일정을 외부에서 검색하거나 신규 28곳 전부를 자동 배치한 결과가 아니다. 식당·카페·숙소는 계속 가상 예시다. 현재 모델은 로컬 Qwen3 8B 하나다. 외부 대형 모델의 제공자·키·호출 경로는 설정되지 않았으며 소형→외부 대형 자동 전환을 실행했다고 설명하지 않는다.

RAG가 중단되거나 자료를 검증하지 못하면 해당 근거를 폐기하고 일반 지식·기존 앱 기능으로 실제 LLM 대화를 이어간다. 화면에도 검색 근거 없이 답변했음을 표시한다. 인사와 일반 질문은 검색을 건너뛴다. 모델이 이미 사용한 자료가 응답 도중 철회된 경우에는 기존처럼 답변 전체를 차단하며, 폐기된 근거를 대형 모델로 우회하지 않는다.

현재 날씨는 정적 RAG 대신 서버의 Open-Meteo 조회 도구로 처리한다. 제주 시내·서귀포·성산·한림·협재·애월·함덕·서울의 고정 좌표와 한국 시간 7일 범위를 사용한다. 모델 기반 현재 상태와 예보이며 관측소 실측이나 산 정상·우도 날씨가 아니다. 지원하지 않는 지역·날짜, 제공처 실패, 오래된 시각·잘못된 단위는 현재 날씨로 대체하지 않는다. 요청 원문·대화·예약 정보는 날씨 제공처에 보내지 않는다. 출처와 조회 시각은 답변 아래 표시한다. 개발 조회의 서비스 조건은 [Open-Meteo 문서](https://open-meteo.com/en/docs)와 [이용 조건](https://open-meteo.com/en/terms)을 따른다.

전송 직후의 대기 질문에도 앵커를 붙이고, 실제 스크롤 pane 좌표·짧은 답변의 읽기 공간·입력창 높이 변화를 처리했다. 긴 대화에서 과거로 스크롤한 뒤 전송해도 새 질문 상단으로 이동하고 응답 완료 후 같은 위치를 유지하는 것을 실제 브라우저에서 확인했다.

자료 확장 직후의 실제 답변 6건은 모델이 status/response/data 등의 임의 포장 JSON을 만들어 모두 계약 검증에서 차단됐다. 원본 질문·조건·후보 ID·모든 검색 본문은 보존하면서 중복 후보 설명과 모델에 필요 없는 출처 메타를 줄이고, 인용은 ref1~ref5로 짧게 전달한 뒤 서버가 실제 근거 ID로 복원한다. 복원 결과도 다시 계약 검증한다. 응답 마지막 위치의 JSON 계약도 보강했다. 원인이 context 창 초과였다는 토큰 단위 실측은 없으므로 확정하지 않는다. 실패 기록은 평가 이력에 남긴다.

일부 모델 답변은 인용 목록을 JSON 배열 대신 본문의 `(evidenceIds: ref1, ref2)` 또는 `(참고: ref1)`에 명시했다. 이 정확한 표기만 인용 배열로 옮기고 표시 문장에서 제거한다. 사용하지 않은 근거를 임의로 인용하지 않으며 알 수 없는 ID는 여전히 차단된다. 혼합 카탈로그 평가에서는 요청한 각 대상에 최소 하나의 공식 요약 인용이 필요하고, 추가적인 체험 설명 인용은 허용한다. 실제 내용 오류·인용 누락·내부 ID 노출은 별도로 검사한다.

같은 원칙으로 모델의 `[ref1](#ref1)` 등 내부 링크·단독 참조 표시는 사람이 읽는 '검색 자료' 표시로 바꾸고, 명시한 ID만 인용 배열에 보존한다. 과거 대화의 근거는 당시 스냅샷 구조로 읽어 원본 제목·URL 변경이나 문서 제거 후에도 대화를 이어갈 수 있다. 화면 링크는 과거의 임의 URL 대신 현재 승인 카탈로그에서만 만들고, 본문이 달라진 경우 이전 자료임을 표시한다. 과거 근거를 새 검색의 승인 자료로 재사용하지 않는다.

내용 시험에서도 한라산의 예약 관리 구간을 전체 코스 출발점으로 오독하거나, 우도 배편 확인에 별개 버스 안내 문서를 섞는 실패를 발견했다. 공식 원본을 다시 확인해 코스·예약 구간·영실/어리목과 백록담의 관계, 항구/도항선의 역할을 더 명확히 요약했다. 특정 명소 설명은 명시한 대상의 자료로 검색 범위를 좁히고 비교는 양쪽 자료를 유지한다. '다른 곳/근처/대안/비슷한 곳' 탐색은 넓은 검색을 유지한다. 이 일반 처리와 별칭 인식은 회귀 검사하며, 코스 시작점 오독·선박 문의를 버스 서비스로 돌리는 답변도 실제 평가의 실패 조건에 추가했다.

RAG는 도구 세션 종료에 묶이지 않는 프로세스로 실행한다. `npm run local:services`는 현재 RAG/Flowise/Ollama의 상태를 검사하고 RAG가 없으면 숨김 백그라운드로 복구한다. 이미 실행 중인 서비스는 재사용하고 다른 서비스가 포트를 차지하면 중단한다. Flowise/Ollama 재설치나 기기 이전은 하지 않는다.

기본 대화 시험에서는 일반 설명을 정상 생성했으나 JSON의 actions만 생략한 응답을 발견했다. 제공자 경계에서 정확히 message(+선택적 evidenceIds)만 있는 JSON을 기존 plain-text 답변과 동일한 actions:[] 읽기 전용 응답으로 취급한다. 임의 wrapper·잘못된 actions·위험한 내용은 복구하지 않고 엄격 검증한다. 3일 일정 시험에서는 모델이 days:3은 정확히 반환하고 숙소 제외 필드를 빠뜨리는 경우를 발견했다. 모델이 이미 build를 요청했고 사용자가 '숙소 추천은 빼줘'처럼 명확히 제외한 경우에만 서버가 해당 configure.lodging:false를 보존한다. 새 build를 임의로 만들거나 '빼지 말고'·방법 설명 요청을 제외 명령으로 바꾸지 않는다.

- Moa: `http://localhost:3001`
- Flowise: `http://127.0.0.1:3002`, native3.1.4 / Node24.22.0
- RAG: `http://127.0.0.1:8765`, Node 내장 SQLite + 실제 임베딩 벡터 cosine 검색
- Ollama: `http://127.0.0.1:11434`,0.40.4
- 해석 모델: `qwen3:8b`, Q4_K_M
- 임베딩: `qwen3-embedding:0.6b`, Q8_0 /1024차원, CPU 전용

현재 Flowise는 같은 Qwen3 8B 가중치의 로컬 alias `moa-qwen3-8b:20261015`를 사용한다. native ChatOllama 노드가 num_predict 입력을 제공하지 않아 Modelfile의 기본 생성 한도를1200토큰으로 고정했다. context12288/temperature0/think:false이며 요청 시간 한도도 별도로 유지한다. 반복 출력 억제는 native 노드의 지원 입력 `repeatPenalty:1.1`, `repeatLastN:128`로 설정하며 alias 가중치·digest·생성 한도는 바꾸지 않는다.

## 초기 13문서 연결 단계의 확인 결과

- native Flowise의 owner 등록·로그인·전용 flow 키 생성·native3노드 graph 생성과 Prediction 실행을 확인했다. Flowise 모델 Credential과 서버→flow 호출 키를 혼동하지 않는다. 이 로컬 Ollama는 외부 provider 키가 없다.
- 앱 연속 검증7건 통과: 일정 생성·카페 이어 담기·예약 언급·DAY2오후만 교체·공개 코스 탐색·정보 부족·서울숲 근거 설명. 이 중6건은 실제 Flowise+LLM+RAG를 호출했고, 정보가 없는 단순 시작1건은 서버 `mode:clarify`로 지역을 먼저 질문했다. AI 실패를 규칙 성공으로 바꾼 경로가 아니다.
- 마지막6개 모델 요청의 전체 왕복은 약2.9–9.9초, 서버 조건 확인은11ms였다. 사례별 값과 모델/프롬프트 버전은 [실제 앱 평가](evaluations/2026-10-15-flowise-rag.json)에 기록했다.
- [RAG 자체 평가](evaluations/2026-10-15-rag.json)는 실제 임베딩 검색7건과 별도 복사 DB의 자료 철회 검증을 통과했다. 원본 DB를 철회하거나 개인 자료를 바꾸지 않았다.
- 인증 누락·다른 키·관리 API 접근 차단을 [실제 인증 검사](evaluations/2026-10-15-flowise-auth.json)로 확인했다. Flowise3.1.4는 Prediction의 Unauthorized를 HTTP500으로 감싸는 upstream 문제가 있다. 정확한 차단 응답을 확인했으며,500이라는 이유만으로 인증 검사 통과로 판정하지 않는다.
- 두 ReAct 노드와 한 Bedrock 노드는 upstream 의존성 경고가 남는다. 이번 native ChatOllama/Prompt/LLMChain 경로는 실행 검증됐으며 Flowise의 모든 선택 노드가 정상이라는 뜻은 아니다.

초기 시험에서는 RAG 후보로 지역을 추측하거나 설명에 잘못된 도구를 넣는 실패가 있었다. 지침과 서버의 좁은 사전 조건 확인을 보완했지만,7건 통과를 다양한 한국어 요청 전체의 정확도로 일반화하지 않는다. `1박2일 일정 만들어줘`처럼 추가 조건이 있는 모호한 문장은 여전히 LLM 경로에서 해석하며 단순 시작용 사전 확인의 범위에 포함하지 않는다.

임베딩 옵션 `num_ctx4096/num_batch64/num_gpu0`을 색인 서명에 포함한다. 8GB GPU는 해석 모델에 사용하고 임베딩은 CPU에서 실행한다. 임베딩 실측 메모리 약1.14GB/VRAM0, 소규모 warm 검색113–194ms였다. 다른 장비나 자료량의 성능으로 일반화하지 않는다.

## 원본·버전·권리 보호

문서·청크·장소 ID와 원문 SHA256, 모델 digest·차원·전처리/옵션·색인 버전을 저장한다. 색인은 후보를 전부 만든 뒤 트랜잭션으로 활성화하고, 실패하면 이전 색인을 유지한다. 모든 awaited 임베딩 확인 이후 하나의 읽기 트랜잭션으로 현재 활성 색인과 사용 허가를 재검사한다.

서버는 RAG SQLite 내부 일치뿐 아니라 `lib/rag-source.ts`로 현재 원본 텍스트와 version hash를 직접 확인한다. 모델 호출 전과 모델 응답 적용 직전에 모두 재검증한다. 삭제·권리 철회 기록은 독립 ledger 테이블에서 차단하며 재색인/이전 색인 선택으로 되살리지 않는다. 외부에서 DB 파일 전체를 예전 백업으로 교체하는 운영 복구 정책은 별도 원본 서버와 맞춰야 한다.

모델의 선택적 `evidenceIds`는 이번 검색 근거의 부분집합만 허용한다. 화면의 ‘검색한 체험 자료’와 ‘설명에 사용’ 표시를 구분한다. 이 ID 검사는 자연어 설명 전체의 사실성을 증명하는 평가를 대신하지 않는다. 좌표·영업·실시간 가격·인기도·실제 이동시간은 제공하지 않는다.

RAG는 Bearer 인증·루프백 바인딩·본문 크기·동시 요청 제한을 사용한다. 검색 질문은2048자까지이며 조용히 자르지 않는다. 모아 입력을 유지한 채 길이 오류를 알려준다. 키는 Git 제외 런타임 설정과 `.dev.vars`에만 있고 브라우저로 전달하지 않는다. 회원 인증·서버 소유 대화 DB·운영 비용/계정 요청 제한은 별도 후속 작업이다.

## 실행 자료

Windows 재구성은 `scripts/flowise/install-windows.ps1`로 프로젝트 안의 Node24와 잠근 의존성을 설치한다. 이후 Ollama/RAG를 실행하고 다음 명령을 사용한다. 기존 owner·키·DB는 보존한다.

```powershell
npm run flowise:prepare-model
```

최종 색인은 `idx:7fd1c882b94b27b178ddc17b1191c44d`, 75문서다. [제주 확장 평가](evaluations/2026-10-15-jeju-expanded-rag.json)는 실제 임베딩 검색 16건과 native Flowise 답변 6건을 같은 색인에서 통과했다. 후자의 답변은 해변·폭포 비교, 송악산 출입, 한라산 코스, 비 오는 날 실내 장소, 우도 이동을 포함한다. 사례별 평가 시각과 동일 색인 확인, 보존한 결과의 hash를 기록했다.

[일정 기능 평가](evaluations/2026-10-15-jeju-actions.json)는 생성·후속 담기·예약 조건·부분 수정·공개 코스·지역 확인·2박 3일 생성 7건을 통과했다. 이 중 지역 확인 1건은 서버 사전 확인 응답이다.
